# Android model PTC entry

English | [中文](tool-isolated-ptc.zh.md)

The original DSH `run_code` is a reserved PTC-mode transport with a generated tool SDK, logs, time budgets, sandbox approval and nested tool execution. Android currently runs the original `ToolRuntime` in native mode. Its proposed `android_ptc` entry is deliberately a narrower product path, not an alias for general `run_code`: the model would supply only `code` and `description`; the App fixes the language to a TypeScript async-function body and the deadline to five seconds. The guest receives no file or network grants and can invoke only the reviewed original `list_agents` direct-child query through `tools.list_agents({ scope: 'children' })`.

At startup, the Android runtime creates an App-owned PTC owner from the native isolated-execution bridge, durable callback journal, original `ToolRuntime`, Agent registry and subagent service. `registerAndroidPtcTool` is called with that owner and a source-controlled product gate. The gate remains `false` pending non-rooted-device isolation, cancellation, callback-retirement and process-death acceptance, so no `android_ptc` schema is registered or callable in the shipped build. This gate is not a model argument, user setting, profile value or remote switch. `runtime.permissions.programmaticTools.modelPtc` reports the unavailable subset and its zero-grant boundary. The original `ptc-runtime`, `workflow-ptc` and `tool-workflow` modules remain protected and disabled.

The conditional definition uses the actual outer `ToolRunContext`. The owner rejects a forged or completed parent using `ToolRuntime.isActiveExecution`, derives the Session and a fresh App-issued zero-grant lease, validates and type-erases the bounded body, and admits one native isolated run. It discovers only the captured first-party `list_agents` definition still registered for that Agent. Before every nested callback, the binding checks the exact registration identity, current Agent, parent token and argument policy; recursive `descendants`, extra fields, replacement registrations and ambient tools fail. The native receipt is projected once by `IsolatedExecutionRun`; a successful result and bounded console logs are rendered without an internal run ID, while cancellation, uncertain retirement and failed receipts publish no result value. Gate revocation during a run also withholds its output. Cordis scope teardown cancels and joins active runs before releasing the native transport.

`node --import tsx --test apps/android/tool/model-ptc-caller-binding.test.mjs apps/android/tool/tool-isolated-ptc.test.mjs` exercises the original AgentLoop, Agent, Session and ToolRuntime against a simulated native transport. It covers conditional registration, the real parent and first-party callback, forged inputs and owner, registration replacement, cancellation, gate revocation, owner shutdown and result withholding. These host tests do not establish Android Binder or UID separation. The device suites in [PTC callback acceptance](acceptance-ptc-callback-device.md) and [workflow process-death acceptance](native-workflow-process-death-device-acceptance.md) still need real device runs. Wider file/network capabilities, original `run_code` behavior and asynchronous workflow execution need separate implementation and acceptance before a general PTC claim.
