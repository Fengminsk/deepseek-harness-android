# Android isolated tool-call port

English | [中文](isolated-tool-call-port.zh.md)

`apps/android/runtime/isolated-tool-call-port.mjs` dispatches reviewed tools for one durably admitted script, PTC or workflow guest. It keeps the guest’s native filesystem and network grants empty. The App owns the exact tool definitions, parent Agent and Session, policy callback, durable journal and result projection; guest code supplies only `{runId,callId,name,arguments}`. Android PTC and workflow remain disabled in `cordis.patch.yml` pending device acceptance.

The port permits host-reviewed `pure` and `read-only` effects. Only a PTC run may additionally call original `write`, `edit` or `android_attachments` with `action: 'materialize'`, classified as `workspace-write`. Those calls require a trusted Session flush function. The caller binding pins definition and registration identities; it rejects a replaced registration even when the same object is registered again. Mixed attachment reviews may lower their maximum write effect to read-only per action, but read-only reviews cannot acquire write authority. Current ToolRuntime policy and the original Android file guards still decide whether a write can proceed. PTC may also dispatch reviewed `linux_exec`, `linux_import` and `linux_export` as `isolated-execution`, with the same durability barriers; `linux_inspect` remains read-only. These names are refused for ordinary script and workflow ports. The [Linux review](model-ptc-linux.md) retains native execution, recovery and approval rules. App-UID shell, nested PTC, workflow, image reading and unreviewed tools remain unavailable through this port.

Calls are serial and limited to 32 attempts; rejected attempts consume their sequence numbers. Each call uses the same Agent, the outer execution token, derived root/sub-call IDs and cancellation signal through the real `ToolRuntime.execute`. Inputs and guest results are limited to 64 KiB; individual audit content, metadata and context snapshots to 128 KiB; guest error text to 4 KiB. A compact guest projection does not remove original host metadata. Oversized metadata yields an explicit unsupported reply after settlement, not a claim that a file was unchanged.

Tool `additionalContexts` are forwarded unchanged to the parent, including failure and cancellation receipts, and retained in the Session audit when bounded. They never enter guest JSON. Images and `concludesTurn` remain unsupported. Original file tools retain a committed-path receipt before observation listeners run; a later observation error or cancellation can therefore preserve the real path. Host post-execute policy may still block that context. In that case the port may know only the requested path; its `verify-before-retry` notice does not invent a canonical path or imply rollback. A mutation failure, cancellation or unsupported reply directs the caller to inspect affected files before any retry. The host never automatically retries a mutation.

For writes and isolated Linux operations, ordering is **journal prepare → Session start event → awaited Session flush → synced dispatch marker → ToolRuntime → observed result marker → Session terminal event → awaited Session flush → journal confirmation → guest reply**. Both flushes must return `true`. A failed first flush prevents dispatch; a failed second flush leaves an unconfirmed result after possible execution or publication. Pure/read-only calls retain the paired Session append and journal ordering without claiming a Session disk-flush barrier. A trusted projection may use `reviewedToolProjectionError(message)` for a bounded, privately registered recovery hint; mutation errors always retain the verification warning.

The App-private journal stores only IDs, names and SHA-256 digests, not file paths or payloads. It claims each run directory exclusively before native binding. Every directory and call marker is non-replayable, including failed binding and confirmed calls. After restart, `prepared` precedes dispatch, `dispatch-unconfirmed` means an effect may have occurred, and `result-unconfirmed` means audit confirmation is incomplete. `confirmed` describes a settled tool envelope, never proof that an errored mutation made no change. The durable Session contains the readable audit and any retained committed-path receipt. Journal and Session writes are ordered, not one atomic cross-store transaction. The [journal snapshot](isolated-tool-call-journal.snapshot.json) documents these states.

Only privately issued policy denials, confirmed tool failures and confirmed unsupported replies become catchable guest errors. Audit, transport and cancellation uncertainty stops the run. `close()` aborts queued/running calls and waits for their actual completion; an unresolved audit fails closure. Native callbacks separately check UID, run identity, nonce, sequence and private admission token. A guest-provided run ID is correlation data, not authentication. Exact tool identities do not defend against malicious same-UID code bypassing ToolRuntime.

Host checks use `node --import tsx --test apps/android/tool/isolated-tool-call-port.test.mjs apps/android/tool/model-ptc-caller-binding.test.mjs apps/android/tool/isolated-tool-mutations.test.mjs`. They cover real ToolRuntime and Session execution, original file tools, JSONL flushes, read-only revocation, post-policy context handling, late cancellation and uncertain results. Windows needs permission for the original atomic file publication primitive. These checks do not establish Android UID/Binder separation, process-death recovery or device filesystem durability; the [PTC execution design](ptc-execution-design.md) owns device acceptance.
