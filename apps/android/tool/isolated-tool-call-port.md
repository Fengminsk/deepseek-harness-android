# Android isolated tool-call port

English | [中文](isolated-tool-call-port.zh.md)

A trusted result projection may throw `reviewedToolProjectionError(message)` with a host-authored recovery hint of at most 4 KiB. The port preserves that privately registered hint in the catchable guest error and the Session error reason, after confirming the unsupported result. Mutating the error object cannot change the registered hint; unknown projection exceptions receive a generic message. A guest can then retry with narrower arguments within the same call budget.

`apps/android/runtime/isolated-tool-call-port.mjs` is a host-side boundary for callbacks from **one already admitted** script, reviewed PTC or workflow guest. The [read-only PTC owner](model-ptc-readonly.md) supplies exact first-party definition reviews and bounded result projections. It does not register `run_code`, start a guest, or authorize a file/network scope. Android PTC and workflow remain disabled in `cordis.patch.yml`.

The original DSH `run_code` accepts a TypeScript async function body and binds the calling agent's visible tools. Its inner calls pass through `ToolRuntime` with a parent execution token, root and sub-call IDs, policy stages, cancellation, and paired session audit. Android's isolated V8 guest accepts a JavaScript function body; the trusted host can now erase erasable TypeScript into that format. The native Binder route can deliver named asynchronous tool callbacks, but no production model-facing caller binds the original `tools.*` set. This port implements one host-owned segment of the original contract, not full language or workflow parity.

The trusted App host constructs the port with a native admission matching the prepared run ID, an **ungranted** normalized guest scope, an outer `ToolRunContext` for the same Session, the production `ToolRuntime`, a finite allowlist, a mandatory per-call `authorizeTool` policy callback and an App-private durable journal. A guest callback supplies only `{runId,callId,name,arguments}`. The `callId` is a monotonic integer consumed even for a rejected attempt; the host derives the session sub-call ID. The port checks exact ownership, plain JSON, size and call count; it rejects names absent from the host allowlist, `run_code`, known ambient App file/Shell/PTC/workflow tools, names no longer visible to the caller, definitions replaced since binding, and calls denied by the current host policy. It serializes subcalls, appends paired `tool/ptc-dispatch-start` and `tool/ptc-dispatch` events, and calls `ToolRuntime.execute` with the outer token and cancellation signal. Successful scalar/JSON results are bounded before reaching the guest. Ordinary materialized tool failures can be caught by guest code. Images, deferred contexts and turn conclusion stay host-only until an explicit parity design exists. Oversized audit content, unrepresentable or oversized guest values, and oversized tool errors are recorded as confirmed unsupported replies; they do not leak to the guest or poison later calls. Audit or dispatch uncertainty poisons the port. `close()` aborts the lane and joins running work; an unconfirmed dispatch makes close fail.

`IsolatedToolCallJournal` writes exclusive, synced files under the App-private `DSH_HOME/isolated-tool-call-journal/<runId>/`. Before the native callback bind, it atomically claims and syncs the run directory; any earlier directory, including an empty directory left by process death, rejects rebinding before another native request. The order is **run claim → native bind → prepare → session start event → dispatch → ToolRuntime → result observed → session terminal event → confirm → guest reply**. Marker contents contain IDs, tool name and SHA-256 digests; they do not contain argument, result or admission-token values. After a restart, `prepared` means dispatch was not entered; `dispatch-unconfirmed` means an effect may have occurred; `result-unconfirmed` means the runtime returned an outcome but the paired audit/guest reply was not confirmed; `confirmed` means the synchronous session append and journal confirmation returned. Every run directory and call marker remains non-retryable, including a bind that failed before its first callback. The App never replays it. The checked-in [keyless state snapshot](isolated-tool-call-journal.snapshot.json) is asserted by the host tests.

The native callback route checks the Binder sender UID, run identity, nonce, call sequence and private App-to-Node admission token. A guest-supplied run ID is only a correlation check, **not** authentication. `NativeIsolatedToolCallbacks` pairs the live native run with this port only after durable admission; cancellation and retirement wait for its `close()` result. Only errors created by the port for a confirmed tool failure, a confirmed unsupported result, or a pre-dispatch policy denial become an exact `{error:{code,message}}` native reply. The App-owned guest `tools.name()` binding raises that reply as a catchable JavaScript error. An exception from audit, transport or cancellation cannot impersonate that reply and still retires the run as uncertain. The App must also select a narrowly reviewed tool allowlist: ToolRuntime policy is necessary but a tool that uses App-UID Shell, unrestricted files or ambient network cannot inherit the isolated script's grants. The port checks the bound definition before entering ToolRuntime, and ToolRuntime pins the registration selected at entry through asynchronous policy and dispatch. A same-name replacement before body dispatch fails as `UNKNOWN_TOOL`; the staged-runtime regression verifies that neither the replacement nor the original body runs. This identity check does not isolate ToolRuntime from malicious same-UID code that mutates a registered definition object or bypasses the runtime. The journal blocks replay but **does not prove whether a dispatched external side effect committed**. `authorizeTool` must return a `pure` or `read-only` classification for the exact bound definition object; a name-only grant, bare effect label or generic boolean is denied. It is rechecked immediately before every dispatch. A thrown policy callback means approval or audit may be uncertain, poisons the run and cannot become a catchable guest denial. This classification is host-authored and does not prove a tool is side-effect-free; each definition still needs an explicit App review before a production allowlist can be bound. The native route accepts at most 32 monotonic calls and requires an empty file/network scope for tool binding. ToolRuntime also relies on each tool obeying its AbortSignal; a non-quiescent tool leaves `close()` pending, with output withheld. Journal confirmation follows the synchronous Session append; no cross-store atomic commit or proof of Session disk flush exists yet. Device UID, Binder death and cancellation behavior remain unverified while a phone is unavailable; workflow still requires a production child-agent integration.

Host validation: `node --test apps/android/tool/isolated-tool-call-port.test.mjs apps/android/tool/native-isolated-tool-callbacks.test.mjs apps/android/tool/isolated-tool-call-journal.test.mjs apps/android/tool/app-owned-model-ptc.test.mjs`. The suite includes a real staged `ToolRuntime`, native callback binding, a child process that exits mid-dispatch, restart replay rejection, mismatched-hash rejection, cancellation and terminal-audit failure. It does not prove Android UID, Binder behavior, device filesystem durability or Session disk persistence. Do not enable the model tool until the device and product gates in [PTC execution design](ptc-execution-design.md) pass.
