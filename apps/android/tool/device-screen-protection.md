# OLED protection during device acceptance

Reference for `device-screen-protection.mjs`. The wrapper uses Android's `cmd display power-off` on every internal panel, including a foldable's disabled panel, and verifies physical `SurfaceFlinger` power modes before starting a device acceptance entry. It does not wake or unlock the phone, change brightness, install an overlay App, or replace the existing black acceptance Activity.

## Screen-only check

```powershell
node apps/android/tool/device-screen-protection.mjs --adb D:\Programs\adb\adb.exe --serial <serial> --seconds 12 --report <report.json>
```

Without `--`, this only samples panel state. Here `--seconds` means the full observation duration after protection is established; the wrapper deadline adds a bounded 60-second allowance for preparation and final verification. Cleanup retains its separate budget. The report includes requested and observed milliseconds and explicitly says no App tests ran. A passing screen-only check does not establish protection during an interactive task, process death or upgrade.

## Running an acceptance entry

Append `-- apps/android/tool/acceptance-<name>-device.mjs` and that entry's arguments. The permitted names are `workflow-lifecycle`, `native-workflow`, `native-workflow-process-death`, `upgrade`, `ptc-process-death`, `ptc-callback`, `linux-vm-lifecycle`, `agent-service-recovery` and `task-completion`. These entries explicitly honor `--adb` and `--serial`. The wrapper inserts the protected target when omitted, rejects duplicate or conflicting values, and sets `ANDROID_SERIAL` for descendants. Other entries fail before touching the phone. Only after all panels report `Off` does the wrapper start the ordinary entries with the current Node executable. Recovery and completion entries retain their cleanup owners in this process and are awaited through cancellation; neither is passed to the killable child launcher. See [locked recovery acceptance](agent-service-recovery-driver.md) for network restoration and its immutable snapshot, and [completion crash acceptance](task-completion-device-acceptance.md) for receipt cleanup and client/device retirement. Each requires a fresh inner result report whose path differs from the outer screen report; completion artifact-only preflight is not an accepted screen-protected workload. In acceptance mode, `--seconds` remains the complete deadline including protection setup, with no additional preparation allowance; it cannot exceed one hour. Run long suites separately. Each entry retains its own preconditions: Activity-based entries require an unlocked, interactive Android session even while panels are off; recovery and completion require an already locked, noninteractive session and never wake it. Completion additionally requires explicit `--allow-existing --installed-only --no-wake`, exact installed App/test APK digests and no App/test processes before admission; it performs no installation.

Samples are normally two seconds apart, plus bounded ADB command latency. Missing USB, changed display topology, handled SIGINT/SIGTERM or any non-`Off` panel immediately starts reapplying power-off to known panels before awaiting child retirement. For ordinary entries, the wrapper requests process-tree termination, waits for the host child's actual close, then force-stops both the App and its test package and checks complete `ps -A -w -o PID,ARGS` names for remaining App, test or isolated-service processes. Normal child completion also performs this device retirement check. A force-stop acknowledgement alone is not proof of retirement. It never clears App data. In-process completion instead passes the guard cancellation signal to `runTaskCompletionEntry`; its independent cleanup must close every owned ADB client and confirm device retirement before the guard may reset display power. A failed or unconfirmed inner cleanup remains a failure, even if notification verification passed.

Ordinary child and device retirement have a 20-second budget, with a separate final force-stop attempt bounded to eight seconds if the host budget is exhausted. Failure or an unreadable process list reports unconfirmed retirement and prevents display-power reset. A failed process-tree kill remains unconfirmed even if the direct child subsequently closes. If the child never closes, bounded cleanup finishes before its host handle is unreferenced; the child may still be alive. The failure records its PID, actual close status and handle release. Unreferencing is not termination evidence. The wrapper provides sampled evidence, not a guarantee against intervening system changes or host termination. Do not count protected foreground tests as proof of background or lock-screen survival.

## Cleanup and recovery

By default, ordinary completion or a handled interruption sends `KEYCODE_SLEEP` and requires every reported wakefulness group to be `Asleep` or `Dozing`. Vendor numeric mirrors accept Android values `0` for `Asleep` and `3` for `Dozing` only when all mirror and named values agree. Values `1`, `2`, missing, unknown or inconsistent states prohibit reset. Only confirmed acceptance retirement permits `power-reset`; a screen-only probe has no acceptance child. Noninteractive state is checked before each reset and again after verifying every physical panel remains off. `Dozing` alone does not prove an OLED is off: resetting an override can restore AOD. A non-`Off` panel after reset fails cleanup and reapplies the overrides. Display cleanup has its own 40-second budget. Any failed reset, unreadable post-reset state or non-`Off` panel triggers a separate power-off attempt for all previously known IDs, even when fresh display enumeration is unavailable. Emergency power-off is bounded to eight seconds. Cleanup failures preserve samples and explicitly mark the final display state unknown. Schema 2 reports successful restoration as `restoredWhileNonInteractive`, not as proof of `Asleep`. Brightness, ambient-display preferences and stay-awake settings are untouched.

For consecutive protected runs, add the valueless `--keep-display-off` before the `--` child separator. Programmatic callers use `restoreDisplayPower: false` in `withScreenProtection`; omitting it preserves the default reset behavior. This mode never calls `power-reset`. It sleeps the phone and requires confirmed acceptance retirement, a stable panel topology, every physical panel `Off`, and a noninteractive state before and after the final panel inspection. A completed screen-only probe has no child to retire. Successful retention reports `retainedWhileNonInteractive: true`, `restoredWhileNonInteractive: false`, and `finalDisplayState: "off"`. The overrides remain active until explicitly released; this is not normal display-control restoration. The report does not guarantee panel state after its final observation.

Retaining overrides does not turn an acceptance failure or cancellation into a pass. Those paths still attempt emergency power-off and await retirement. If final checks succeed, the error report can confirm retained `Off` separately from the failed test. Missing or unconfirmed retirement, unreadable or non-`Off` panels, changed topology, or an interactive phone keeps the run failed, attempts power-off for all known panels, and reports retention unconfirmed with `finalDisplayState: "unknown"`. An acknowledged power-off command alone is not physical `Off` evidence.

An interrupted host or USB disconnection can leave overrides active and retirement or cleanup unconfirmed. Before explicitly releasing retained overrides or recovering a failed cleanup, confirm that the previous host acceptance process and all target App/test processes have retired. After reconnecting, keep the phone fully asleep, inspect `cmd display get-displays --ids-only --type internal --category android.hardware.display.category.ALL_INCLUDING_DISABLED`, and issue `cmd display power-reset <id>` for each returned ID. Confirm physical panels remain `Off` with `dumpsys SurfaceFlinger` before resuming tests. If AOD or another non-`Off` state returns, reapply `cmd display power-off <id>` to all internal panels and keep the overrides; do not claim restoration or change system AOD preferences. Never substitute `power-on` or reset the App's data. The focused host tests run with `node --test apps/android/tool/device-screen-protection.test.mjs`; they do not replace device evidence for interactive or upgrade workloads.
