# Isolated workflow callback transport

English | [中文](native-workflow-guest-callbacks.zh.md)

`NativeWorkflowGuestCallbacks` is a Node host endpoint for one already admitted workflow and one App-issued private token. The native `native.workflow.bindCallbacks` acknowledgement is required before it accepts `WORKFLOW_BEGIN`, `WORKFLOW_START_CHILD`, `WORKFLOW_CHILD_RESULT`, `WORKFLOW_DISPOSE_CHILD`, or `WORKFLOW_PROGRESS`. Each frame must match the admitted run ID and token and carry the next call ID, with no replay after close.

Up to four runs may be bound. Each run accepts at most 128 callbacks, with at most eight awaiting dispatch. The host snapshots each JSON request at a 64 KiB limit before reserving its call ID, then dispatches accepted calls in call-ID order. It bounds each reply to 64 KiB before returning it to native code. A rejected oversized or saturated request does not consume the next call ID. Closing cancels and retires the child port, then drains admitted callbacks; failure to retire a child remains a failed close.

The App-side matching protocol is `IsolatedWorkflowRequest` and `IsolatedWorkflowCallbackBridge`. Its relay must have a `DurableWorkflowOwner`, verify the Binder sender UID and exact run identity, and recheck `ADMITTED` before callback and reply publication. The guest only receives the existing `host.callAsync` JSON channel; it receives no App file path, Node object, or ambient tool API.

The internal `native.workflow.admit/bindCallbacks/execute/cancel/settle/release` route reserves both a script and workflow receipt before replying, binds an App-issued token, runs through the isolated-script controller, and publishes only a matching durable terminal state. `AgentService` routes the reverse `native.workflowCallback` and `native.workflowCallback.cancel` requests to Node. `NativeWorkflowPrivateOwner` requires the prepared Session ID to match its live parent, writes the original `tool-workflow/run-start` record after admission, and flushes each accepted member start/end through `SessionStore.flush` before acknowledging progress. It writes and flushes `tool-workflow/run-end` only after child retirement, native settlement and release are confirmed; missing storage confirmation or uncertain cleanup leaves an open run. The Binder relay persists a new child UUID and `LAUNCHING` state before sending `WORKFLOW_START_CHILD`; Node uses that UUID for the original `startActivation` with the model-only preset. `WORKFLOW_CHILD_RESULT` returns bounded content, while `WORKFLOW_DISPOSE_CHILD` marks the receipt retired only after the original activation has joined.

On Agent Service startup, the App acquires the exclusive runtime process lease before reconciling old workflow receipts and starting Node. It exposes newly interrupted and unretired-child counts in `runtime.status.workflowRecovery`; this startup snapshot does not replace per-Session `workflow.inspect` for older review cases. Unreadable receipts block workflow admission without stopping unrelated App work. An exit before Node admission clears the lease marker rather than reporting a crashed Node generation. Cold recovery never replays a guest, and a stranded child ID blocks new workflow admission until a backend confirms that child stopped. After a confirmed callback close during cancellation, a child reserved but not launched can also be retired.

The private `workflow.inspect` RPC reads a bounded physical prefix of the exact parent Session through a read-only persistence handle. A recorded `run-end` gives the terminal state; an open run with a matching in-memory owner is running; an open run after owner teardown is `interrupted-unconfirmed` and requires review. An attached Session without a matching owner, changing ownership, an oversized history, or conflicting events fails closed as `unconfirmed`. Inspection never resumes an Agent, replays a guest, or appends a synthetic `run-end`. It is a diagnostic contract, not an automatic continuation or a UI recovery flow.

**There is still no model-facing workflow caller.** The child runs under the App UID with a scoped zero-tool preset; that preset does not provide a separate OS UID or full filesystem/network sandbox for arbitrary child code. The private guest supports the original workflow hooks within narrower limits, and its Session records use the original event vocabulary. Session append is not an independent fsync-backed workflow progress journal. Ordinary isolated scripts remain limited to five seconds; only the App-owned private workflow route may request up to 120 seconds, and the scope lease must cover that deadline. This finite guest bound does not by itself establish general model inference parity. Device acceptance, especially process death and callback races, remains outstanding. The original model-facing `ptc-runtime`, `workflow-ptc`, and `tool-workflow` remain disabled.
