# Isolated JavaScript engine foundation

English | [中文](isolated-ptc-script-engine.zh.md)

[`PtcScriptEngine`](../android/app/src/main/java/com/minnnng/dsh_android/PtcScriptEngine.java) is a V8-only JNI engine used by the internal [isolated script run controller](isolated-script-run.md). It is **not connected to DSH `run_code` or workflow**, and does not add a model-visible tool. The Android PTC and workflow profile entries remain disabled.

The caller supplies a JavaScript **function expression**, such as `(input) => ({count: input.count + 1})`, and one JSON input value. Native V8 compiles a private snapshot function before guest code and keeps its handle outside the guest global object. Every returned value passes through this function before JSON encoding. It detaches plain JSON data and rejects lossy shapes such as `undefined` fields, holes, non-finite numbers, `-0`, accessors, non-enumerable/symbol properties, custom prototypes and cycles with `OUTPUT_INVALID`. The snapshot captures built-ins before guest code can replace them, and tests cover an inherited descriptor-property forgery.

DSH's Node provider accepts an async function **body** with erasable TypeScript, top-level `await` and `return`, captures `console` logs, supports declared binding namespaces, and can use Node modules under its sandbox policy. Android now has a separate `runFunctionBody` entry for **plain JavaScript statements** with top-level `await` and `return`; Successful runs capture bounded `console.log/info/warn/error/debug` text lines. TypeScript stripping, Node modules, persistent REPL and failure-log retention remain unsupported. The original complete JavaScript function-expression entry still works. The new entry obtains V8's built-in `AsyncFunction` constructor before guest code, supplies the body as its own string argument rather than interpolating it into a surrounding expression, then disables string code generation **before invoking user code**. This avoids the delimiter-escape flaw found in a discarded wrapper prototype. The body receives only JSON `input` and, in the host-enabled overload, the optional `host` object backed by an explicit App-issued grant; the default overload exposes no host object. No model-facing route invokes this engine. A fresh V8 Isolate and context execute one function call and return compact JSON. A Promise can settle through V8 microtasks; an unresolved Promise returns `ASYNC_HOST_UNAVAILABLE`. There are no timers, event loop, Node Environment, `process`, `require`, `fs`, `net`, `child_process`, `fetch`, Android bindings or ambient broker calls. Guest string code generation and WebAssembly compilation are disallowed. This is a restricted compute primitive, not a compatible replacement for the original direct-Node PTC provider.

The Java API is `new PtcScriptEngine()` → `run(program, inputJson, deadlineMillis)` **or** `runFunctionBody(body, inputJson, deadlineMillis)` → `Result {status, outputJson, logsJson}` → `close()`. Either run method blocks the caller thread and the instance may be used only once; `cancel()` may be called from another thread before or during execution. Only one native execution may be registered per guest process. A closed or cancelled instance cannot be reused. The caller must bound its Binder/service operation separately and treat guest process death as failure. The engine's native resource is owned by `close()`; a close during execution interrupts it and retains the registry slot until the running call exits.

The expression or body and input are each capped at 64 KiB UTF-8, encoded console logs at 16 KiB, combined logs and returned JSON at 64 KiB UTF-8, and elapsed script deadline at 1–5000 ms. An exceeded output budget returns `OUTPUT_TOO_LARGE` without publishing partial logs or JSON. This is deliberately shorter than the original Node provider's 120-second default and 600-second maximum. The native-held snapshot caps traversal at 8192 values and 64 levels. Every run uses a new V8 heap with 16 MiB old-generation and 4 MiB young-generation targets, an aggregate 8 MiB ArrayBuffer allocator limit, no `Atomics.wait`, and a watchdog that calls `TerminateExecution()` for deadline or cancellation. V8 may terminate the whole isolated process on heap exhaustion; these V8 limits are **not** a hard bound on total native RSS. Status values distinguish invalid request/input/program, script failure, invalid/large JSON output, unsupported pending async, deadline, cancellation and engine unavailability. No partial JSON is returned on failure.

The engine is linked against the pinned `libnode.so` only to use exported V8 symbols. It never calls `node::Start`, initializes a Node Environment, or maps App-private workspaces into the guest. Future PTC integration must add a versioned, bounded host-call Promise bridge to App-side capability brokers, durable invocation/result logging, strict grant lifetime, child-agent ownership, and a separate provider descriptor that states the restricted JS contract. It must also prove on a normal non-rooted device that native loading works under an isolated UID and that infinite loops, allocation pressure, cancellation, deadline, malformed input, Binder death and process kill settle one terminal result. Native compilation and host Java checks alone do not satisfy those gates.

Host checks: `node apps/android/tool/acceptance-ptc-script-engine.mjs` validates Java request bounds, checks independent AsyncFunction-body grammar against prior wrapper escapes, and evaluates the exact native snapshot source in a restricted host V8 context against original PTC completion-value fixtures, including hostile prototype mutation; it does not load JNI. `node apps/android/tool/acceptance-isolated-script-run.mjs` checks versioned durable receipt round trips for bounded logs. `:app:externalNativeBuildDebug` compiles and links the JNI library against the pinned Android V8 export set. The separate `PtcFunctionBodyInstrumentation` test APK entry checks JNI execution, ambient globals, restored code-generation denial, syntax escapes and lossless output on a device; it has only been compiled, not run. The existing isolated-guest acceptance remains necessary to prove distinct UID and Binder behavior.
