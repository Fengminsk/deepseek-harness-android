# Android PTC and Workflow confinement

This reference describes why the Android profile refuses model-authored PTC programs and workflow scripts. The Android App runs an embedded Node host under the application UID. That UID protects the App from other applications; it does not restrict a child program to the selected workspace or prevent that child from reading the App's private files.

The original [`NodePtcRuntime`](../../../packages/ptc-runtime/ptc-runtime-node/src/index.ts) permits direct Node filesystem, network, and subprocess APIs. For `workspace-write` it calls `ctx.sandbox.confine()` before spawning a worker. The original [`sandbox-local`](../../../packages/sandbox/sandbox-local/src/index.ts) selects a runner for Linux, macOS, or Windows and refuses platforms without a runner. Android has no runner in that selection. Switching the policy to `danger-full-access` skips confinement and is not equivalent to the original PTC contract.

The Android profile keeps the PTC provider, workflow engine, and workflow tool disabled. [`stage-preset.mjs`](stage-preset.mjs) rejects a packaged profile that enables any of them. [`host-guard.mjs`](../runtime/host-guard.mjs) rejects active rows in the composed profile, including profile and home overrides, ordinary module aliases, and nested preset plugins, before starting the native carrier. The Android runtime also reserves these packaged module identities through `pluginManager.protectModules`, so ordinary plugin-management edits cannot toggle them later. These checks validate the packaged configuration and module identities; they do not confine arbitrary third-party plugin code or a distinct module implementing similar behavior.

An Android implementation needs a worker isolated from the App UID, an explicit bridge for authorized workspace files and tool calls, bounded output, and termination that observes every descendant. The App declares an [`isolatedProcess` service](https://developer.android.com/guide/topics/manifest/service-element) with an App-only `runtime.isolation.probe` call: the host grants a read-only regular file of at most 256 KiB through Binder, checks the Binder sender UID, digest, and inability to read a separate App-private marker by path, then grants a read-only descriptor for a strict UTF-8 read capped at 64 KiB. [`IsolatedWorkerBridge`](../android/app/src/main/kotlin/com/minnnng/dsh_android/IsolatedWorkerBridge.kt) accepts a descriptor already opened by the App, never a worker-selected path; each request has an identity, five-second deadline, and cancellation message before unbinding. The App can snapshot an explicitly selected relative workspace file, including nested directories, and grant its bounded text descriptor for a literal edit or literal search. Search returns bounded line previews, locations, a truncation flag and the snapshot revision; edit commits against that SHA-256 revision through [`IsolatedWorkerWriteback`](../android/app/src/main/java/com/minnnng/dsh_android/IsolatedWorkerWriteback.java). Both operations reject malformed UTF-8, excess input or output, invalid paths and cancellation; edits also reject excess replacements and stale writeback. The diagnostic probe exercises the edit path; host Java tests and Android Kotlin compilation cover the added code, but device execution remains unverified. Bridge calls serialize writes across their writer instances, but other same-UID writers can still race between the final revision check and rename, or replace a parent directory after validation. This transport is a foundation, not a PTC executor. The Node subprocess provider and PTC control channel still do not launch workers through that Service, map general workspace operations or tool callbacks through Binder, or contain descendant processes. A separate Android JavaScript isolate could serve the workflow script subset, but it does not preserve PTC's documented direct Node API behavior.

Acceptance for enabling the original capability includes an Android worker launch with a distinct UID, allowed workspace reads and writes, denied App-private and out-of-workspace file access, controlled network/subprocess behavior, nested binding approval and logging, cancellation and timeout with descendant cleanup, owner release, and restart recovery. Host tests of profile rejection do not establish those device behaviors.
