# Android PTC and Workflow confinement

This reference describes why the Android profile refuses the original unrestricted Node PTC provider and workflow plugins. The separate [reviewed android_ptc entry](model-ptc-readonly.md) and [native workflow entry](tool-native-workflow.md) use isolated guests and explicitly reviewed ToolRuntime callbacks; both are source-enabled in the Build 116 candidate, whose workflow-enabled production profile remains pending verification. The Android App runs an embedded Node host under the application UID. That UID protects the App from other applications; it does not restrict a child program to the selected workspace or prevent that child from reading the App's private files.

The original [`NodePtcRuntime`](../../../packages/ptc-runtime/ptc-runtime-node/src/index.ts) permits direct Node filesystem, network, and subprocess APIs. For `workspace-write` it calls `ctx.sandbox.confine()` before spawning a worker. The original [`sandbox-local`](../../../packages/sandbox/sandbox-local/src/index.ts) selects a runner for Linux, macOS, or Windows and refuses platforms without a runner. Android has no runner in that selection. Switching the policy to `danger-full-access` skips confinement and is not equivalent to the original PTC contract.

The Android profile keeps the original Node PTC provider, workflow engine, and workflow tool plugins disabled. [`stage-preset.mjs`](stage-preset.mjs) rejects a packaged profile that enables any of them. [`host-guard.mjs`](../runtime/host-guard.mjs) rejects active rows in the composed profile, including profile and home overrides, ordinary module aliases, and nested preset plugins, before starting the native carrier. The Android runtime also reserves these packaged module identities through `pluginManager.protectModules`, so ordinary plugin-management edits cannot toggle them later. These checks validate the packaged configuration and module identities; they do not confine arbitrary third-party plugin code or a distinct module implementing similar behavior.

An Android implementation needs a worker isolated from the App UID, an explicit bridge for authorized workspace files and tool calls, bounded output, and termination that observes every descendant. The App declares an [`isolatedProcess` service](https://developer.android.com/guide/topics/manifest/service-element) with an App-only `runtime.isolation.probe` call: the host grants a read-only regular file of at most 256 KiB through Binder, checks the Binder sender UID, digest, and inability to read a separate App-private marker by path, then grants a read-only descriptor for a strict UTF-8 read capped at 64 KiB. [`IsolatedWorkerBridge`](../android/app/src/main/kotlin/com/minnnng/dsh_android/IsolatedWorkerBridge.kt) accepts a descriptor already opened by the App, never a worker-selected path; each request has an identity, five-second deadline, and cancellation message before unbinding. On API 29+, each operation binds a uniquely named isolated Service instance and observes Binder death; API 28 uses ordinary binding to the declared `isolatedProcess` Service, retaining the separate UID but allowing service-instance reuse. Both paths unbind on completion. The App can snapshot an explicitly selected relative workspace file, including nested directories, and grant its bounded text descriptor for a literal edit or literal search. Search returns bounded line previews, locations, a truncation flag and the snapshot revision; edit commits against that SHA-256 revision through [`IsolatedWorkerWriteback`](../android/app/src/main/java/com/minnnng/dsh_android/IsolatedWorkerWriteback.java). Both operations reject malformed UTF-8, excess input or output, invalid paths and cancellation; edits also reject excess replacements and stale writeback. The diagnostic probe exercises the edit path; host Java tests and Android Kotlin compilation cover the added code, but device execution remains unverified. Bridge calls serialize writes across their writer instances. App-side writeback now requires [Android SecureDirectoryStream](https://developer.android.com/reference/java/nio/file/SecureDirectoryStream): workspace segments are opened without following links, and reads, staging, deletion and replacement remain relative to the same open parent directory. A provider without secure directory operations fails closed. The staged file type, inode key and SHA-256 are checked after close and immediately before rename; the published target is checked again before returning a clean receipt. A detected post-rename mismatch or directory-sync failure is reported as CommitUncertain. Directory identity is checked around the rename and path-based durability callback. These checks do not make a hostile same-UID writer safe: it can still replace the staged name after the final check but before renameat, or modify the target after the published check. Renameat has no inode/content compare-and-swap. Another same-UID writer can also change the target between its revision check and rename, and a moved parent can make path-based directory sync uncertain. These narrow races can escape detection, so this is not an adversarial same-UID or race-free commit guarantee. Windows host tests use a relative-operation adapter because its default provider does not implement SecureDirectoryStream; only an Android device run can verify the real provider and race behavior. This transport is a foundation, not a PTC executor. The Node subprocess provider and PTC control channel still do not launch workers through that Service, map general workspace operations or tool callbacks through Binder, or contain descendant processes. A separate Android JavaScript isolate could serve the workflow script subset, but it does not preserve PTC's documented direct Node API behavior.

The architecture and admission gates for general execution are in the [PTC execution design](ptc-execution-design.md). The App-side bounded file-call foundation now has an internal, policy-leased Binder bridge to the isolated V8 guest, as described in the [isolated capability broker](ptc-capability-broker.md) and [script host bridge](isolated-script-host-bridge.md). The separate reviewed model entry uses the isolated guest and bounded original tool callbacks. It does not make the original direct-Node PTC scripts executable.

Acceptance for enabling the original capability includes an Android worker launch with a distinct UID, allowed workspace reads and writes, denied App-private and out-of-workspace file access, controlled network/subprocess behavior, nested binding approval and logging, cancellation and timeout with descendant cleanup, owner release, and restart recovery. Host tests of profile rejection do not establish those device behaviors.

The Android-private workflow owner exposes `modelAdmission` through [`model-workflow-admission.mjs`](../runtime/model-workflow-admission.mjs). The separate [native workflow factory](tool-native-workflow.md) captures the original tool contract, exact live definition and registration identity, current ToolRuntime execution and parent Agent; Session identity comes from the Agent, never model input. It rechecks the execution and registration after asynchronous App policy decisions and consumes an opaque single-use ticket rather than exposing a native request to the model. The isolated DSL receives no direct file or network grants; reviewed child tools intersect live parent and child permissions. Explicitly authorized background execution uses the original jobs registry and preserves creating tool-call identity. The Build 116 candidate sets `MODEL_WORKFLOW_DEVICE_ACCEPTED=true` after r26 normal workflow (11/11), deadline/child-retirement and process-death checks passed. The original Node plugin remains disabled. The production profile with `expectWorkflow=true` and ordinary Build 116 upgrade remain pending; the earlier r25 390-second hang has no confirmed cause and is not erased by later success.
