# Android PTC 与 Workflow 的进程隔离

本文说明 Android 配置为何拒绝原版不受限 Node PTC 执行器及工作流插件。独立的[受审查 android_ptc 入口](model-ptc-readonly.zh.md)及[原生 workflow 入口](tool-native-workflow.zh.md)使用隔离客体与显式审核的 ToolRuntime 回调；两者均已在 Build 116 候选源码中开放，包含 workflow 的正式 profile 仍待验证。Android App 内嵌的 Node 宿主以应用 UID 运行。这个 UID 让其他应用无法直接访问本应用数据，但不会把子程序限制在选定工作目录，也不会阻止它读取应用私有文件。

原版 [`NodePtcRuntime`](../../../packages/ptc-runtime/ptc-runtime-node/src/index.ts) 允许直接使用 Node 文件系统、网络和子进程 API。在 `workspace-write` 模式下，它先调用 `ctx.sandbox.confine()`，再启动执行程序。原版 [`sandbox-local`](../../../packages/sandbox/sandbox-local/src/index.ts) 只为 Linux、macOS 和 Windows 选择隔离执行器；平台没有执行器时会拒绝运行。Android 当前没有对应执行器。把策略改成 `danger-full-access` 会跳过隔离，不能视作实现了原版 PTC 行为。

Android 配置保持原版 Node PTC 提供方、工作流引擎和工作流工具插件为禁用状态。[`stage-preset.mjs`](stage-preset.mjs) 拒绝打包时启用这三项。[`host-guard.mjs`](../runtime/host-guard.mjs) 在原生宿主启动前检查合成配置，拒绝配置目录和主目录覆盖、常规模块别名及预设内的激活项。Android 运行时还使用 `pluginManager.protectModules` 保留这三项已打包的模块标识，普通插件管理操作也不能在启动后开启它们。这些检查只验证已打包的配置和模块标识；它们无法隔离任意第三方插件代码，也无法阻止另一个模块自行实现类似行为。

Android 上实现这项能力需要将执行程序隔离于 App UID，通过明确的桥接接口访问已授权工作文件和工具调用，限制输出，并在结束时确认全部子进程退出。App 已声明一个 [`isolatedProcess` Service](https://developer.android.com/guide/topics/manifest/service-element)，并提供仅限 App 调用的 `runtime.isolation.probe`：宿主通过 Binder 授予不超过 256 KiB 的只读普通文件，检查 Binder 发送方 UID、内容摘要及其是否能通过路径读取另一份 App 私有标记，然后再次授予只读文件描述符，验证最多 64 KiB 的严格 UTF-8 文本回传。[`IsolatedWorkerBridge`](../android/app/src/main/kotlin/com/minnnng/dsh_android/IsolatedWorkerBridge.kt) 只接收 App 已打开的文件描述符，不接受工作进程选择的路径；每次请求都有独立标识、五秒期限，失败时先发送取消消息再解绑。在 API 29 及以上，每次操作绑定名称唯一的隔离 Service 实例，并监听 Binder 死亡；API 28 使用已声明 `isolatedProcess` 的普通绑定，仍保持独立 UID，但可能复用 Service 实例。两种路径都会在操作结束时解绑。App 可对明确选中的工作目录相对路径文件生成快照，包括嵌套目录，并将有界文本描述符授予独立 UID 的工作进程进行字面编辑或搜索。搜索返回有界的行预览、位置、截断标记与快照版本；编辑由 [`IsolatedWorkerWriteback`](../android/app/src/main/java/com/minnnng/dsh_android/IsolatedWorkerWriteback.java) 按 SHA-256 版本写回。无效 UTF-8、超限输入或输出、无效路径及取消均被拒绝，编辑还会拒绝超量替换和过期版本。诊断探针覆盖编辑路径；新增代码通过主机 Java 测试和 Android Kotlin 编译，设备执行仍未验证。桥接写入在本进程的多个写入器之间串行化。App 侧写回现在要求 Android 的 [`SecureDirectoryStream`](https://developer.android.com/reference/java/nio/file/SecureDirectoryStream)：工作目录各层不跟随符号链接，读取、暂存、删除和替换都相对于同一个已打开的父目录；文件系统不支持安全目录操作时拒绝写回。暂存文件关闭后、重命名前会核对其普通文件类型、inode 标识与 SHA-256，并在替换后重新核对目标文件；检测到的替换后内容不符或目录同步失败均以 `CommitUncertain` 报告。重命名前后以及按路径执行持久化回调前后还会检查目录身份。但这无法抵御恶意同 UID 写入者：它仍可在最后一次检查与 `renameat` 之间替换暂存文件名，或在替换后的检查完成后修改目标；`renameat` 不提供按 inode 或内容比较并交换。同 UID 写入者还可在目标版本检查与替换之间改动目标；已打开的父目录若被移动，按路径执行的目录同步也可能无法确定。这些极窄竞态可能逃过检测，因此不能宣称对抗式同 UID 隔离或无竞态写回。Windows 主机测试因默认文件提供者缺少 `SecureDirectoryStream` 而使用相对操作适配器；真实提供者及目录竞态行为仍需 Android 设备验证。这项传输能力只是基础，不是 PTC 执行器。当前 Node 子进程提供方和 PTC 控制通道仍不能通过该 Service 启动，通用工作目录操作和工具回调尚未通过 Binder 桥接，也无法约束后代进程。独立的 Android JavaScript 隔离环境可以考虑承载工作流脚本的受限子集，但不等同于 PTC 所承诺的直接 Node API。

通用执行的架构与逐项准入条件见 [PTC 执行设计](ptc-execution-design.zh.md)。App 侧受限文件调用基础现已通过受策略租约约束的内部 Binder 桥连接隔离 V8 客体，详见[隔离能力代理](ptc-capability-broker.zh.md)和[脚本宿主桥](isolated-script-host-bridge.zh.md)。独立的受审查模型入口使用隔离客体与有界原版工具回调；它不使原版直接使用 Node 的 PTC 脚本变得可执行。

启用原版能力前，需要在 Android 设备验证独立 UID 启动、允许的工作目录读写、拒绝访问应用私有文件及工作目录外文件、受控的网络与子进程行为、嵌套工具的审批和记录、取消及超时后的后代进程清理、持有者释放和重启恢复。主机上的配置拒绝测试不能证明这些设备行为。

Android 私有工作流持有者通过 [`model-workflow-admission.mjs`](../runtime/model-workflow-admission.mjs) 提供 `modelAdmission`。独立的[原生 workflow 工厂](tool-native-workflow.zh.md)捕获原版工具契约、准确的实时定义与注册身份、当前 ToolRuntime 执行及父 Agent；Session 身份来自 Agent，不接受模型输入。异步 App 策略决定后会再次核对执行与注册，消费不透明的单次票据，不向模型暴露原生请求。隔离 DSL 不获直接文件或网络授权；受审查子工具取实时父子权限交集。经显式授权的后台执行使用原版 jobs 注册表，并保留创建它的工具调用身份。Build 116 候选在 r26 常规 workflow（11／11）、时限／子级退役及进程死亡检查通过后，将 `MODEL_WORKFLOW_DEVICE_ACCEPTED` 设为 `true`。原版 Node 插件仍禁用。`expectWorkflow=true` 正式 profile 与普通 Build 116 升级仍待验证；此前 r25 的 390 秒挂起尚无确认原因，不因后续成功而删除。
