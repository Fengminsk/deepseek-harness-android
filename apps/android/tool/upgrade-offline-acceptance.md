# APK upgrade, offline, and process-restart acceptance

[中文](upgrade-offline-acceptance.zh.md) | English

Android APKs omit Windows native binaries. To run the packaged JavaScript on a Windows host, this harness adds two Windows test bindings from staged packages after confirming identical package metadata. The JSON result reports this substitution.

`node apps/android/tool/acceptance-apk-upgrade-offline.mjs [previous.apk] [current.apk]` runs a **host** check using the runtime ZIPs inside two real APKs. The default inputs are the Build 54 archived APK and the current debug APK. The extractor verifies each APK's embedded runtime SHA-256, rejects unsafe ZIP paths and links, and boots the older and newer Android profiles in independent Node processes against the same durable home. Network traffic is restricted to a synthetic loopback account/model server. The older process signs in, completes one model turn, persists its Session, then starts a second streaming turn and is killed before completion. The newer runtime cold-starts offline, reopens the account grant and both Sessions, retains bundled models, and does not replay browser login, token exchange, or either inference. Reconnecting refreshes the model directory without replay; another cold restart checks idempotence. The new runtime also survives a separate interrupted streaming turn across two offline cold boots without duplicating the prompt or inference. To limit disk use, it extracts the previous runtime first, stops that process and removes its generated extraction, then extracts the new runtime; the shared durable home remains in place for the test and the two runtime hashes must differ. After all fixture processes stop, the generated home and temporary ZIP copies are removed by default. Pass `--retain-home` to keep the fixture for an explicit audit; the JSON result reports whether it was removed.

Run `python apps/android/tool/extract-apk-runtime.test.py` for extractor negative controls. `node apps/android/tool/task-recovery-smoke.mjs` separately covers termination during a live stream and an unanswered Shell approval, unknown tool outcomes, suspended queued prompts, and no automatic replay. `node apps/android/tool/account-recovery-smoke.mjs` separately covers HTTP 503, transport loss and account rejection on the current staged profile. `node apps/android/tool/acceptance-document-access.mjs` covers host-testable SAF read limits and version checks. They are different evidence: do not combine their green results into a claim that Android process death, package-manager upgrade, Keystore, or ContentResolver persistence was tested.

Device-only acceptance still requires installing the previous APK with a real account, completed and in-flight tasks, and a persisted SAF tree grant; disconnecting and reconnecting the network; force-stopping or killing the Agent process; installing the newer APK **without clearing app data**; and checking account state, model listing, Session content, suspended task state, grant access/revocation behavior, notification state, and absence of duplicate model/tool side effects. Capture package versions, APK hashes, `dumpsys package` data directory identity, task/session IDs, and timestamps. A host check cannot assert that a real Android upgrade retains package data or that OS process death invokes `Service.onDestroy`.

The first SAF text page creates an immutable app-private snapshot and reopens the provider document once to compare SHA-256. Continuations read that same content-versioned snapshot, so a same-size/same-modification-time replacement cannot be spliced into subsequent pages. Each page still checks the persisted grant, relative path, document URI, and provider metadata; a revoked grant or moved document invalidates continuation. Opening offset zero again captures a fresh content version. A snapshot is limited to 256 MiB; the cache is limited to 512 MiB and eight entries, expires after 30 minutes of inactivity, and reserves 128 MiB of device free space. A cache cleared by Android, expired by time, or evicted for new snapshots requires restarting at offset zero. Page reads and eviction in the same app process share a critical section so an in-use snapshot is not concurrently removed; external OS cache clearing may still invalidate the next read. A provider that silently replaces bytes after capture while retaining its URI and metadata leaves the old snapshot visible until the user reopens it. Real ContentResolver provider behavior, cache survival across process restarts, and grant-revocation races still need device evidence.

SAF directory listing and name-based path resolution each stop after 10,000 returned children. Relative paths are limited to 4,096 characters and 64 levels before provider traversal; an oversized directory or deeper path reports that the user must grant a closer subdirectory through the system picker. The host document-access check covers these limits, while provider cursor behavior remains a device-only check.
