# Isolated script host-call bridge

English | [中文](isolated-script-host-bridge.zh.md)

`IsolatedScriptRunController.run` accepts optional App-owned file and network policies. A file policy contains an App-private workspace root, durable `IsolatedCapabilityJournal`, opaque owner ID, exact file grants and a sandbox policy. A network policy contains an exact HTTPS host set, durable `IsolatedNetworkJournal`, deadline-aware resolver and pinned TLS transport. Either capability requires an active `IsolatedExecutionPolicyOwner` whose single admission callback durably writes its one-use script receipt. Before binding a fresh isolated service, the controller checks that the requested grants, exact hosts and separate file/network call budgets fit the admitted lease. A network-only scope needs no file workspace or grants. Without either policy, V8 receives only the input value and no host object. The owner must not reconstruct these policies from model text or expose this overload as a model tool.

The JavaScript function receives `(input, host)`. `host.grants` contains random file-grant IDs and actions but no paths; it is empty for a network-only scope. `host.call({action, callId, grantId, ...})` makes one synchronous Binder request. `READ`, `SEARCH` and `EDIT` map to the App-side file broker, which retains paths and audits each call. `host.call({action:'HTTPS_GET',callId,url})` maps to the App-side network broker, which accepts only exact allowlisted HTTPS hosts, pins resolved addresses to the selected Android Network and audits each call. The request cannot carry headers, credentials, body, an arbitrary method, IP literal or alternate scheme. Each call has a caller-owned canonical UUID, consumed even on rejection. The guest still has no ambient filesystem, Node, subprocess or network API. Pending promises and named asynchronous DSH PTC bindings are unsupported.

The guest sends at most one outstanding request, with a monotonically increasing sequence bounded to 128 calls, a 32 KiB JSON request, the script run ID and nonce, and a reported UID. The App checks Binder's actual sender UID, the reported UID, run identity, exact fields and sequence before dispatch. Separate file and network counters enforce the admitted budgets. The App's 448 KiB result contains structured status and bounded data; this envelope covers worst-case JSON escaping of a 64 KiB file read or network response. Network text is returned as `bodyText`; non-UTF-8 bytes are base64 encoded as `bodyBase64`. An oversized body settles as `RESPONSE_TOO_LARGE`. The guest verifies the matching reply before resuming V8. The engine's output remains capped at 64 KiB and its execution deadline at five seconds. Cancellation revokes both brokers, wakes a waiting callback and prevents a late result from becoming script success. `COMMIT_UNCERTAIN` for a file edit or `AUDIT_UNCERTAIN` for a network call withholds script output and requires inspection before retry.

The App proposes completion only after the script result and no outstanding host call. It accepts success only after guest Binder death, binding cleanup, applicable terminal audit and script receipt sync. A per-lease file publication lock orders cancellation against replacement; cancellation during a blocked rename marks the run unconfirmed even if it later finishes. A host worker that does not quiesce, uncertain cleanup or failed audit settlement withholds output. Recovery recreates neither grants nor network calls. General PTC/workflow remains disabled, and App-UID Shell is outside this isolated guest. Host checks and Android/JNI plus instrumentation compilation have run; isolated UID, Binder sender attribution, Android DNS/TLS, file/network operations and process-death behavior still need non-rooted device acceptance.
