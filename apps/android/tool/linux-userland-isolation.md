# Android Linux userland execution boundary

English | [中文](linux-userland-isolation.zh.md)

## Purpose and current behavior

A small Linux userland can make an Agent's command environment more predictable: a shell, common text tools, language runtimes and a stable command vocabulary. It is a compatibility layer, not a container security boundary. The current Android App embeds Node under the App UID and ships an App-UID `/system/bin/sh` path for explicit diagnostics. That path has no filesystem or network confinement and is unavailable as an ordinary model tool. One `isolatedProcess` service runs bounded V8 scripts without Node or ambient file/network access. A separate isolated command service now executes a small, fixed Android utility catalog through an App-owned Binder bridge; it accepts bounded stdin and literal arguments but no shell source, host path or direct network grant. The fixed `android_linux` Agent tool reaches this command bridge, but has not passed device isolation tests. Neither path currently runs a Linux distribution or provides a model-facing general shell. See [Shell policy](../runtime/shell-execution-policy.mjs), [native shell supervisor](../android/app/src/main/cpp/shell_supervisor.c), [script engine](isolated-ptc-script-engine.md), and [PTC execution design](ptc-execution-design.md).

## Separation of duties

| Component | Responsibility | Authority it must not inherit |
| --- | --- | --- |
| Trusted App and Node host | Own task state, approvals, account credentials, image inventory, audit and recovery | No model-authored command executes in this UID |
| Linux guest service | Run one admitted command under a fresh isolated UID where supported | No App-private path, `ContentResolver`, account token or direct Binder authority outside its run protocol |
| File and network brokers | Mediate approved workspace reads/writes and exact-host HTTPS under one issued policy | No guest-selected raw App path, unrestricted socket or implicit broad directory grant |
| Userland image | Provide verified, pinned executable bytes and data, with per-ABI identity | No privilege, sandbox promise or dynamic package installation during a run |

The App issues a one-run policy through the [sandbox projection](isolated-sandbox-policy.md): read-only with network denied by default, or explicitly approved workspace write roots and exact HTTPS hosts. The guest may only request operations within that scope. A child task can only narrow it. File writes, including protection of `.git`, `.agents`, `.codex` and `.aws`, must be enforced by the App-side operation broker, even if the userland can see a broad virtual path. The guest must not receive a writable bind mount to the App home or workspace. The current V8 bridge is a useful protocol foundation; it does not automatically give native Linux processes its bounded host-call API.

The [Linux guest broker precheck](linux-guest-sandbox-policy.md) projects a live lease into virtual file paths and exact HTTPS hosts. It grants no direct mount or socket; each operation still needs the App-owned broker. The [broker wire contract](linux-guest-broker-wire.md) bounds and identifies proposed file/HTTPS requests. The [dormant Binder transport](linux-guest-binder-transport.md) verifies the isolated Service identity, but has no native guest frame producer. The [launch-session accounting](linux-guest-launch-session.md) rejects success without a verified isolated UID, broker settlement and complete process-tree retirement evidence. The [run journal](linux-guest-run-journal.md) reserves IDs durably and keeps a candidate result private until the completion marker is synced. These components are not connected to an executable guest yet.

## Runtime contract

Admit a request only after checking a packaged or downloaded image's signature or pinned digest, ABI, manifest version, binary count, unpacked byte limit, traversal and link targets, and executable provenance. This App targets API 36; Android forbids `execve()` of ELF files extracted to writable App home for apps targeting API 29 or higher. Executable launchers and native tools therefore must be APK-packaged code, while a downloaded image may supply verified non-executable data only. See [Android's executable-file restriction](https://developer.android.com/about/versions/10/behavior-changes-10#execute-permission). The App can verify and install the inert archive atomically, but its isolated Service cannot be assumed to unpack and traverse App-private storage: [Android 16 isolated-app policy](https://android.googlesource.com/platform/system/sepolicy/+/android16-release/private/isolated_app_all.te) forbids direct App-data file opens. The current [staging preflight](linux-guest-staging-recovery.md) fails closed, and the [storage options](linux-guest-storage-options.md) require a new path before Alpine execution. Pin a specific image revision for every run. Image validation establishes code identity, not guest confinement.

The App records `runId`, parent task, image revision, issued policy ID, exact command/arguments, deadline and output budget before starting the guest. The guest receives only that immutable request and explicit broker handles. No environment variable from the App's Node process is copied; provide a fixed `PATH`, locale, temporary directory semantics and a virtual working directory that is not mistaken for a file permission boundary. Output is framed, capped and attributed to the run. A success result is durable only after guest exit, pending broker calls, child processes and audit writes have settled. Cancellation, timeout, Binder death, App death and package upgrade must all yield an explicit terminal or `outcome-uncertain` state rather than an invented success.

The optional [native supervisor source](linux-guest-native-supervisor.md) prepares a fixed diagnostic command and an OS-owned event pipe. It is disabled in ordinary builds and has no Service caller.

Userland selection should be staged. First validate direct execution of a tiny, APK-packaged Bionic-compatible tool set in the isolated UID on a normal device. The current candidate uses an Alpine musl root filesystem and a separately built PRoot launcher; it cannot be activated until device proof shows how the isolated UID reads guest data, how ELF execution respects Android W^X, and how syscall translation and every descendant are retired. See the [candidate status](linux-proot-candidate/STATUS.md), [tracee protocol](linux-proot-candidate/EVENTS.md), and [distribution gate](linux-proot-candidate/DISTRIBUTION.md). PRoot changes path semantics for the guest but does not enforce App workspace, network or credential policy. A full distribution adds storage, startup, update and supply-chain costs; it should be optional and versioned separately from the base App. The Android Virtualization Framework is not a fallback for an ordinary third-party App: its VM APIs require the restricted `MANAGE_VIRTUAL_MACHINE` permission ([AOSP framework notes](https://android.googlesource.com/platform/packages/modules/Virtualization/+/refs/tags/aml_net_351410000/libs/framework-virtualization/README.md)). A future WASI interpreter may run bounded WASM programs under separate capabilities, but it cannot execute Alpine ELF programs and must not be advertised as a Linux VM.

The fixed Alpine/PRoot [source-bundle evidence](linux-proot-candidate/SOURCE-BUNDLE.md) supports later distribution review; its verification does not approve packaging or execution.

## Required device evidence before broader guest access

On a non-rooted device, demonstrate the actual guest UID and denial of App-private files, out-of-scope workspace files and direct network sockets. Demonstrate allowed broker-mediated reads, revision-checked writes and exact-host HTTPS only after approval. Run shell pipelines, a process that creates descendants, a new-session attempt, large output, allocation pressure and a hanging command; cancel and kill the service, then prove no descendant continues or records a late side effect. Repeat after backgrounding, offline operation, process termination and APK/image upgrade. If the platform cannot reliably contain or account for descendants, a general userland command tool remains unavailable and the isolated V8 PTC subset may still operate separately.

No user-facing label should say “Linux container” or “workspace sandbox” until the device evidence supports those claims. A userland image can make commands easier for an Agent, but its safety comes from the isolated UID and the App's file, network, process and lifecycle controls.
