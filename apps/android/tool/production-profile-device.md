# Android production profile acceptance

[中文](production-profile-device.zh.md)

This reference covers the keyless `production-profile` suite in [packaged Node acceptance](device-runtime-acceptance.md). The fixture imports the shipped `bootstrap.mjs`, which launches `dsh --profile android` and registers tools through the shipped Android `index.mjs`. It does not register substitute PTC, workflow or Linux tools. Only the model HTTP endpoint and credentials are synthetic; AgentLoop, Session, ToolRuntime, native dispatch and isolated execution use their normal implementations.

Each run creates a UUID home under `noBackup/native-runtime-acceptance` and a dedicated workspace directory. Native credentials use an isolated memory map containing one synthetic API key and the validated browser-session secret generated by the original Connection plugin during startup; account and unrelated credential writes are rejected. The fixture never opens the user's credential store. Model and closure authentication use independent random 32-byte secrets stored only in the dedicated home; proof and diagnostics never include them. Closure also checks the case nonce. The local Messages server binds only `127.0.0.1`, requires the model key, limits request bytes and accepts a fixed sequence. The real model receives `android_ptc` and `linux_exec` definitions; Linux must omit `networkHosts` and `networkCallLimit`. PTC reads the created workspace file, then Linux executes Python with `hashlib`, `sqlite3` and `zipfile`. Matching tool-result IDs, content, distinct guest UID and confirmed retirement are required before the model sends its final reply.

The default `expectWorkflow=false` requires workflow to be absent. Explicit `expectWorkflow=true` requires the actual build to expose workflow and adds one foreground workflow call. One child Agent receives a dedicated prompt and returns its marker through the real model protocol. The fixture checks the matching workflow result, one child request, parent run/member completion events and a separate durable child Session. This parameter never changes product availability.

Request authentication precedes run-state changes and body parsing. Requests without either purpose-specific secret receive 401; only a bounded rejection count and the latest method/path are recorded, so unrelated local probes cannot fail or advance the authenticated turn. An authenticated request with an invalid method, path or closure case still fails the suite. Request diagnostics exclude headers and query strings, cap method/path lengths and redact both fixture secrets.

The suite requires `foregroundCarrier=service` and a locked, noninteractive device. It opens no Activity and does not wake or unlock a display. Run it only inside the existing [physical-panel protection and process-retirement owner](device-screen-protection.md). The acceptance service keeps the test process scheduled; it is not evidence of production `AgentService` background survival. Exclude the App from the device's background-freeze policy before a run: an OEM freezer can suspend it under a locked, panel-off state, and such a run is an environment result rather than product evidence. The host must join the owned ADB invocation, force-stop only the test's App/test process owners and verify final whole-process retirement. Framework lock/display observations are not pixel or physical-panel proof.

```sh
adb shell am instrument -w -r -e suite production-profile -e foregroundCarrier service -e expectWorkflow false com.minnnng.dsh_android.test/com.minnnng.dsh_android.NativeRuntimeToolsAcceptanceInstrumentation
```

Use `runProductionProfileAcceptance({ invoke, signal, expectWorkflow })` from [the host driver](acceptance-production-profile-device.mjs) inside that outer owner. `invoke(args, signal)` supplies the selected device and returns bounded stdout only after its ADB child closes; abort or unknown child retirement must reject. The driver validates native cleanup and returns explicit remaining obligations for physical-panel observations and Node retirement. The native suite budget is 360 seconds without workflow or 480 seconds with it; the model turn has a separate bound. An execution failure requests Session cancellation and retains cleanup failures as suppressed errors. Model disposal awaits listener closure and outstanding request handlers.

The result records shipped bootstrap/runtime hashes, model tool-schema hash, matching Session IDs and dedicated JSONL file hashes. Success requires a completed durable turn containing PTC dispatch and Linux execution, the final response, a closed model listener, and the carrier's actual native-owner closure. Retained fixture files contain only synthetic input and protocol evidence. Host protocol/parser tests and standalone Kotlin compilation do not establish device acceptance; retain the actual instrumentation result and outer retirement/display report before making that claim. This suite does not verify public model credentials, Linux networking, upgrades, production background survival or general workflow lifecycle limits.

Startup diagnostics record fixed checkpoints, monotonic elapsed time, the awaited RPC, native/notification method names, runtime failure phase and errno, model counters, bounded socket addresses/families and matched interface identity, and bounded stack locations. The [fixture bootstrap](device-runtime-acceptance/production-profile-bootstrap.mjs) and [JVM scenario](../android/app/src/androidTest/kotlin/com/minnnng/dsh_android/ProductionProfileAcceptanceScenario.kt) own the additional observations below. Diagnostics omit credential values, request headers, prompts and model bodies.

During the shipped bootstrap import, the fixture records load start, return or failure for three fixed modules: the CLI, profile boot and Android runtime entry. A returned load hook confirms loading, not completion of module evaluation or an internal CLI/Loader wait. The `nodeStartup` snapshot records module states, fixed artifact-presence flags, a one-second unreferenced event-loop pulse and cumulative process CPU deltas since observation began, in microseconds. Pulse and elapsed fields use milliseconds from the fixture clock; the observer records its inactive state when it closes. A missing or stale snapshot cannot distinguish event-loop blockage, scheduler delay, process suspension or delayed diagnostic writes by itself.

The JVM `readyWait` probe samples on an independent daemon thread around the unchanged `ready.get(90, TimeUnit.SECONDS)`. It records the entry `System.nanoTime()` value, relative finish/timeout and pulse times in milliseconds, maximum pulse gap and `samplerStopped`. Timeout records when the waiting thread observes the timeout; it is not proof that the scheduler delivered it at exactly 90 seconds. Node and JVM observations use separate clock origins, so compare intervals within each clock rather than subtracting their absolute values. The test probes acquire no wake lock or runtime authority; missing pulses or a large gap do not establish Doze, deadlock or a root cause. Sampler cleanup failure remains a failure, including as a suppressed error when the ready wait already failed.

The local socket must be an explicit loopback address. A peer must be `127.0.0.1`, `::ffff:127.0.0.1` or `::1`, or match an exact unicast address in a fresh `os.networkInterfaces()` snapshot for that request. Missing snapshots, absent addresses, wildcard/multicast addresses and unassigned remote addresses are rejected; no subnet or stored device IP is allowed. Every admitted address still requires its purpose-specific secret. A failed runtime initialization fails the ready wait immediately. Missing model proof or an unsuccessful closure response is reported as unconfirmed listener retirement; it cannot silently pass cleanup. The [JVM scenario check](acceptance-production-profile-host.mjs) exercises the actual scenario with Android SDK JSON sources; host results do not establish Android process behavior or resolve the retained r28 startup failure.

## Build 116 r28 device observations

The two retained runs used the same App SHA-256 `5cd11e06ab70a170235971f7a0140c982db992acf2c3c368066752e7089c7b41` and AndroidTest SHA-256 `74d913413f36559cb9272df2bbfe2ae1c614e8878cbd5a024010e75091399b0e`. Their result files are `.cache/android/production-profile-116-r28-protected-20261028.json.result.json` and `.cache/android/production-profile-116-r28-warm-20261028.json.result.json`; each has an outer screen/retirement report at the same path without `.result.json`.

The first run failed at `runtime-ready-wait` after reaching `production-bootstrap-import-start`. Its failure records 287,158 ms elapsed against the ready wait's configured 90 seconds, zero native calls, zero notifications and no model calls. A cooperative `CompletableFuture.get(90, TimeUnit.SECONDS)` observes its timeout only when the waiting thread runs again, so the 197-second excess is a suspension of the whole process rather than a slow start. On 2026-10-28 the installed Build 120 showed the same App state: `AgentService` was a foreground service (`isForeground=true`, `foregroundServiceType=specialUse`) while the device's `OplusHansManager` froze both App processes with `cgroup.freeze=1` under scene `|StrictMode-3|LcdOff`, and AMS still reported `isFrozen=false`. That OEM freezer is outside the App's control. `AgentService` now bounds startup readiness at 120 seconds and records observed suspensions, so a repeat reports an attributed failure instead of an unknown stall. Later closure and outer retirement do not turn this run into a pass.

The subsequent run labelled `warm` passed in 15,462 ms with `expectWorkflow=true`: four parent model requests, one child request, PTC workspace reading, Linux Python analysis and workflow completion. It retained two separate durable parent/child Session JSONL files. The Linux guest UID was 99478 versus App UID 10496; guest retirement and model-listener closure were confirmed. These are actual shipped-profile operations driven by the synthetic model endpoint.

The warm outer report records nine samples with both physical panels `Off`, noninteractive restoration, a closed host command and confirmed disappearance of target processes. The in-process `nodeProcessRetired` field remains false; whole-process retirement is supplied separately by that outer report. Warm success does not explain or erase the first failure. Neither run certifies real account authentication, a public model provider, production background survival or long-duration Doze behavior. The [115→116 upgrade record](upgrade-116-acceptance.md) covers its separate data-retention checks.

## Build 116 r32 stalled diagnostic run

The retained `.cache/android/production-profile-116-r32-diagnostic-20261028.json` reports failure after the owner stopped the stalled acceptance. Its companion `.result.json` contains `shortMsg: Process crashed.` and no native result; it supplies no successful profile evidence. The outer report confirms host close and device-process retirement after stopping, which does not change that outcome.

At the read-only capture in `.cache/android/production-profile-r32-scheduler-01.json`, PID 31829 had actual `cgroup.freeze=1` and `cgroup.events` with `frozen 1`, while PowerManager reported `isFrozen=false` for the acceptance partial wake lock. That wake-lock field did not establish that the process could run. The OEM-freezer observation recorded under the r28 section attributes that cgroup state to the device's `oplus_freeze` service, which freezes the App while AMS reports no freeze; the capture itself still does not date the freeze or demonstrate a scheduling fix. The owner stopped its acceptance processes without changing device freeze policy.
