# Isolated execution approval history

English | [中文](isolated-execution-approval-store.zh.md)

[`IsolatedExecutionApprovalStore`](../android/app/src/main/java/com/minnnng/dsh_android/IsolatedExecutionApprovalStore.java) is an App-private persistence adapter for the internal [`IsolatedExecutionPolicyOwner`](isolated-execution-policy-owner.md). It starts with a denied version 1 scope, writes every later scope and approval identifier to a checksummed, chained history, and returns only a denied scope after reopening. If the last durable scope was granted, reopening first records a new denied version. An interrupted or uncertain grant is never reactivated by recovery. The store does not read model text or accept guest Binder calls.

The caller supplies an existing directory within the App-private root and a directory-sync operation. A process-wide file lock permits one writer. Each transition rewrites the bounded history through a synced temporary file, atomic replacement, and directory sync; unpublished temporary files are discarded on reopen. The history has at most 256 transitions, 1 MiB total and 16 KiB per scope. Corruption, an unknown owner or Session, an unresolved filesystem failure, an exhausted history or a concurrent writer prevents admission; existing evidence is not silently reset. A completed approval identifier cannot be used again in that history.

The trusted App UI must verify a specific user choice before calling `prepareTrustedUiApproval(next, approvalId)` with a fresh UUID. `PolicyOwner.replace(next)` then consumes that one prepared decision and synchronously persists the exact scope before it becomes active. A granted transition without a matching prepared decision is rejected. `IsolatedScriptRunController.newPolicyOwner` opens this store, binds its one owner to the one-use script receipt store, and returns an `ApprovalHandle`; file and network host runs reject an owner not issued by this factory. The only grant API, `approveTrustedUiChoiceForRun`, additionally binds the owner to one canonical run ID. An internal native caller must prepare an exact pending request in `IsolatedExecutionApprovalInbox`. Flutter may display its complete App-private workspace path, relative read/write scopes, hosts, budgets and expiry, but cannot submit a new scope. A foreground `MainActivity` confirmation sends a separate native Binder message with the pending challenge; ordinary JSON-RPC calls cannot grant. The store records that decision but cannot independently prove a human tap. No production caller currently prepares these requests, so the UI shows an empty state; instrumentation uses synthetic test approvals.

Closing the store revokes its issued owner. Process death releases the file lock; reopening verifies the entire history and records a denied version before returning any owner. If the revocation cannot be durably recorded because of corruption, capacity or I/O uncertainty, reopening fails closed and requires operator inspection. The record does not restore a live lease, grant App-UID Shell confinement, or enable the original PTC/workflow tools. The new review UI, native confirmation and storage path still need device-level validation before use by a production script request.

Run `node apps/android/tool/acceptance-isolated-execution-approval.mjs` for host checks of fresh consent preparation, single-owner locking, approval ID replay, crash-style restart revocation, uncertain sync, damaged history, temporary-file cleanup and capacity. Run `node apps/android/tool/acceptance-isolated-execution-approval-inbox.mjs` for exact-scope display, duplicate and stale challenge refusal, one-use approval, revocation and expiry. These are host filesystem checks, not Android power-loss or device execution evidence.
