# App-owned isolated execution policy

English | [中文](isolated-execution-policy-owner.zh.md)

[`IsolatedExecutionPolicyOwner`](../android/app/src/main/java/com/minnnng/dsh_android/IsolatedExecutionPolicyOwner.java) holds an immutable policy snapshot for the internal isolated script runner and a future PTC or workflow provider. A new owner starts at version 1 with no file scope and no network host. Its owner and Session IDs are fixed, and each run has a canonical UUID, a bounded lease, call budgets, an exact App-resolved workspace root when files are granted, relative readable and writable scopes, and exact HTTPS hostnames. The file and network policies are independent: a network-only scope needs no workspace. The guest must receive only the run ID and opaque broker handles, never either root pathname. This class has no model-facing caller and does not control the existing App-UID Shell, DSH file tools, or plugins.

The trusted App must verify a user choice before it constructs a nonempty scope. The class delegates path validation to `IsolatedCapabilityBroker.SandboxPolicy` and hostname validation to `IsolatedNetworkBroker.Policy`; it verifies that a selected workspace resolves within an existing App-private root. The file broker still must use descriptor-anchored, no-follow operations at every call because a pathname check at policy creation cannot prevent later filesystem changes. A child run can only narrow its parent's path scopes, host set, call budgets and lease; nesting stops at 16 levels, and the owner retains at most 128 live leases. Replacing the current policy requires the same owner and Session ID and exactly the next version. Replacement closes admission and removes every live lease before invoking revocation hooks or the App's `DurableTransition` callback; a reentrant hook cannot admit a run under the old version. If that callback fails, the owner refuses all later admissions and retains no live lease. The callback can write to disk, so the App must invoke replacement off the main thread.

`IsolatedScriptRunController.newPolicyOwner` now opens the durable approval store and binds `DurableAdmission.reserve` to the one-use script receipt store. A file or network host run requires that controller-issued owner as well as its host policy. The controller calls the owner once, verifies the same run ID was durably admitted, and does not admit the receipt a second time. If reservation fails, the owner revokes every existing lease and refuses further admission until a new owner is constructed from recovered durable state. It rejects a host policy whose owner, workspace, grants, or file-call budget exceed the active lease before binding the guest. Revocation or a policy version change rejects subsequent host calls and prevents a completed result from being published; final receipt publication is serialized with policy replacement. The file broker and per-lease publication gate separately settle an in-flight edit, returning an unconfirmed outcome when cancellation overlaps publication. The controller revokes the lease after the run. Its pure JavaScript path still uses the receipt store directly and has no host object.

The owner does not restore live scopes. App process death discards every lease, and script receipt recovery marks an unfinished run uncertain without replay. The [approval history store](isolated-execution-approval-store.md) persists policy versions and revokes recorded grants on restart. The controller's grant API binds a reviewed scope to one run ID; the App now has an internal pending-review UI and a foreground native confirmation path, but no production code prepares a script request for that UI. The guest must terminate when its App reply Binder dies; the owner alone cannot stop a process or undo an already committed file or network effect. Existing App-UID Shell, DSH file tools and plugins remain outside this policy; no model-authored PTC or workflow tool is enabled.

Run `node apps/android/tool/acceptance-isolated-execution-policy.mjs` for host checks of default deny, immutable scope, reservation callback ordering and failure, restricted child inheritance, version invalidation, revocation, failure closure, path and host validation, and restart without authority. Android instrumentation also includes one-run approval binding, file-policy replay and revocation checks, but has only compiled, not run on a phone. Host checks do not establish Android UID isolation, Binder death, SAF behavior, or actual approval durability. A normal non-rooted device run and end-to-end App approval acceptance are required before this policy can govern model-authored work.
