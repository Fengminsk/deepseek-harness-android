# Locked AgentService recovery acceptance

[中文](agent-service-recovery-driver.zh.md)

`acceptance-agent-service-recovery-device.mjs` drives installed instrumentation through real ADB. Without an exercise argument, it runs `AgentServiceRecoveryInstrumentation`: the production AgentService creates a dedicated idle Session and verifies its unchanged event count and SHA-256 across offline and restored connectivity, without a model request. Opt-in `radio-linux` selects `AgentServiceTaskAcceptanceInstrumentation` for one real-account task. Both use `agent-service-recovery-driver.mjs` as the single owner of network changes, restoration and process retirement; neither establishes model HTTP retry or recovery after service death.

## Entry and protection

Use an already locked, noninteractive phone with an initially validated network. The driver reads `dumpsys power` and the scoped `KeyguardServiceDelegate` before instrumentation. It refuses interactive, unlocked, ambiguous or unavailable state. It never sends wake, sleep or unlock input. `--no-wake` documents this mandatory behavior; omitting it does not enable waking.

```powershell
node apps/android/tool/device-screen-protection.mjs --adb D:\Programs\adb\adb.exe --serial <serial> --seconds 420 --report <screen-report.json> -- apps/android/tool/acceptance-agent-service-recovery-device.mjs --accept-network-toggle-and-lock --no-wake --report <recovery-report.json>
```

The screen wrapper binds `--adb` and `--serial` to its own target. This entry runs in the wrapper's process through an awaited import, not through its killable Node child path. Guard cancellation reaches the driver as an AbortSignal; physical panel protection is reapplied immediately, while the guard waits for the driver's independent cleanup before resetting display control. The generic child launcher explicitly rejects this entry. Standalone invocation requires explicit `--adb`, `--serial`, `--report` and the network-toggle consent flag, and handles SIGINT/SIGTERM through the same cleanup owner. Use the wrapper to obtain physical screen protection.

## Opt-in active Linux call

Add `--exercise radio-linux --accept-real-account-request` to the same protected entry only when a real account request is authorized. Both arguments are required together, in addition to `--accept-network-toggle-and-lock`; omission preserves the idle Session exercise. The direct echo adapter also retains its no-radio default. Account admission, the exact 40-second Python command and durable completion checks belong to [account-task acceptance](agent-service-task-device.md#radio-linux).

Radio readiness binds the original case, Session, generation, Agent PID and pending `linux_exec` call. The `tool/call` record precedes scheduler preparation and does not show that Python has started. After both radios are confirmed disabled and the network classifier finds no underlying INTERNET network, the driver collects at least two offline task observations spanning at least 15 host-monotonic seconds from completion of the first offline sample. Each rechecks the same PID, running parent task, pending call, locked state and disabled flags. `offlineSamples` retains these observations; `timing.minimumDwellMs` is `15000`. The driver restores the original flags and observes usable connectivity before sending `restored`. It then awaits the original turn's final Linux receipt and persisted assistant reply, rather than submitting another model request.

The [radio validator](agent-service-task-radio.mjs) checks each checkpoint and final task result independently. The protocol does not create another network cleanup owner: failure, timeout, signal or screen-guard cancellation still enters the same restoration and process-retirement path below. The 15-second native offline-to-restored requirement also remains enforced. Pending-call observations and the final guest receipt do not establish continuous Python execution during the outage, guest network access or retry of an interrupted model HTTP stream. The [r34 account-task record](agent-service-task-device.md#radio-linux-r34) owns the passing device result and its limits.

## Evidence and restoration

Before starting instrumentation, the adapter reserves a new report and writes an immutable `<report>.original.json` containing the device serial, random token and exact `wifi_on` / `mobile_data` configuration flags. Existing reports and snapshots are not overwritten. Both flags must be `0` or `1`, with at least one enabled. The screen and recovery report paths must differ. This configuration snapshot does not claim which subscription or transport supplies validated connectivity; the original native fixture separately observes Android's validated network count.

Instrumentation emits token-bound progress for service start, binding, runtime readiness, Session operations and checkpoints. The host retains the last complete record as `lastProgress` and its phase as `nativeStage`, including on timeout, and writes only validated, sanitized progress to `<report>.progress.json`. That file contains no raw transcript, account secrets or model text and is not a success result. The fixed fields contain a sequence, PID, monotonic elapsed/uptime counters and a filtered runtime summary, with background details in idle progress; unknown fields, stages, tokens and replayed sequences are rejected without retaining their contents. Elapsed time includes device sleep; uptime excludes it. Neither counter alone proves that a particular process was frozen. In idle mode, every five seconds while the main Looper runs, a diagnostic request reads the existing native `runtime.status` endpoint, including `bootStage`, task counts and wake-lock state; radio pulses instead report the cached runtime observation from the readiness/observation loops, without another RPC or background details in `progress.runtime`. In both modes, `runtimeObservedAtMs` distinguishes a fresh response from a retained snapshot. This observation acquires no wake lock and does not change production startup or task policy. The host's 150-second ready wait includes native readiness and dedicated-Session RPCs; radio also waits for the model's validated pending tool call. It is not a measurement of Node startup alone. Partial lines remain pending, and malformed progress cannot prevent independent cleanup.

Every idle-exercise observation must retain the original Session ID, runtime generation, event count and digest, and report `locked=true`, `interactive=false`. Radio instead preserves the original active task and call identity while new completion events are expected. The production Agent PID must remain the same in both exercises. Network evidence schema 2 records anonymous network handles, SDK-known transport enums, INTERNET / VALIDATED / VPN / NOT_SUSPENDED flags, the App default network and separate aggregate counts. It omits capability object dumps, SSIDs, IP addresses and UID lists. `RecoveryNetworkEvidence.java`, included only in AndroidTest, classifies INTERNET + VALIDATED + non-VPN networks without restricting transport; Ethernet, USB and other internet transports count too. The host recomputes every count from the supplied facts.

The host checks the same Agent PID after readiness, at the offline checkpoint and after restored-network observation, before sending the `restored` command that permits instrumentation to finish. `processChecks` retains these observations and radio's additional offline checks. The final idle checkpoint must still retain the same Session/generation/hash and locked state; radio requires its validated completed task evidence. Both must archive the dedicated Session, return a unique success result and close the host process. The target PID need not survive expected instrumentation finish; final process retirement is independently checked during cleanup. `timing` records host-monotonic checkpoint offsets and the span from online to restored observation. The 15-second observation-response limit is not a dwell period: idle retains `minimumDwellMs: 0`, while radio separately enforces the interval above. Idle point observations do not certify a 15-second outage or an active task; neither exercise establishes prolonged suspend/Doze survival.

Before restoring connectivity, both saved network flags must actually read disabled and no non-VPN INTERNET network may remain. An IMS network without INTERNET or a persistent validated VPN overlay does not establish usable underlying internet, but both remain visible in the evidence. Unknown capabilities and unvalidated non-VPN INTERNET networks also block offline acceptance, since lack of validation does not establish lack of access. Initial and restored checkpoints require at least one INTERNET + VALIDATED non-VPN network and no unknown capabilities. Network classification itself uses Android capability observations, not an HTTP probe; radio's separate model request can consume account quota. The final native result must be unique and successful with its exercise-specific Session evidence; its ADB process must actually close successfully.

Each ADB command has an eight-second deadline and up to 3.5 seconds of additional close observation. Cancellation of a dispatched `svc` mutation waits for that command's bounded settlement; it does not race an immediate restore against an abandoned mutation. A failed mutation receipt leaves the network outcome unknown, even if later flags happen to match. Independent cleanup attempts both original flags, checks exact readback for up to 15 seconds plus bounded command latency, then force-stops App and test packages, waits up to 20 seconds for actual host close, and checks full App/test/isolated-service process names for up to 20 seconds plus command latency. No data is cleared. Instrumentation has a separate 330-second host deadline. Radio's native work remains bounded by 300 seconds, its turn by 120 seconds and its native cleanup by at most 60 further seconds; the host deadline can interrupt that cleanup and still requires independent restoration and retirement.

Cleanup does not inherit the cancelled work signal. The driver reports network restoration, host close and device retirement separately; any failure yields `result: unknown`. Reports preserve the failing phase, last checkpoint and network facts, bounded nested execution/cleanup/cancellation causes, and native failure causes when available. An unclosed child is unreferenced only after bounded cleanup and remains explicitly unretired. Unknown restoration or retirement prevents the screen wrapper from resetting panel overrides. Failed report persistence preserves these facts in the thrown error and prints a fallback JSON diagnostic. Hard host termination or unavailable USB cannot be made recoverable by an in-process `finally`; use the immutable snapshot to restore the exact original flags after reconnecting, and verify device processes and panel state before resuming work.

## Host checks

```powershell
node --test apps/android/tool/recovery-network-evidence.test.mjs apps/android/tool/agent-service-recovery-driver.test.mjs apps/android/tool/device-screen-protection.test.mjs
```

These keyless tests exercise parsing, cancellation, partial changes, ambiguous receipts, exact restoration and retirement through controlled IO. The network test compiles and executes the actual AndroidTest Java classifier on a host JVM. They are not device acceptance evidence or an Android APK build. A real report is emitted by the ADB adapter with `evidence: device-adb`; preserve failed reports and use a new report path for each device attempt.
