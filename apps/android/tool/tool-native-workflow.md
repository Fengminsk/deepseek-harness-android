# Android native workflow registration

English | [中文](tool-native-workflow.zh.md)

`registerAndroidWorkflowTool` registers the original `workflow` parameter, result and presentation contract through `createWorkflowToolDefinition`. The App supplies the executor and a build-owned availability function; its default is closed. No profile value, model argument or user credential can open that gate. Production `index.mjs` keeps `MODEL_WORKFLOW_DEVICE_ACCEPTED=false`; importing this module alone registers nothing. The system prompt permits workflow use only when the user explicitly asks for workflows or multi-agent orchestration.

`modelWorkflowCapability` reports the maximum reviewed child tool set as `read`, `glob`, `grep`, `write`, `edit`, `web_search`, `web_fetch`, `linux_exec`, `linux_import`, `linux_export` and `linux_inspect`, with `childTools: 'reviewed-parent-tools'`. This is not a guarantee that any tool is present for a particular parent or child, nor permission to invoke the closed production entry. Linux tools require existing parent registrations; `LINUX_VM_DEVICE_ACCEPTED=false` keeps them absent in production. The capability describes the activation workspace and parent/child policy intersection, inherited web providers, and an offline child-Session-private Linux disk. The model-facing tool description and system prompt identify these conditional tools and their restrictions.

Each invocation captures the exact current ToolRuntime definition and registration identity, checks the live parent Agent and its real Session ID, and consumes one App-owned admission ticket. The App issues an ungranted DSL scope with a 120-second deadline, at most eight children and two concurrent children. The original JavaScript DSL runs through the fixed isolated guest, not in the Node host. Child tools use a separate Host grant; they do not give the DSL direct filesystem or network access.

Children retain the parent model route and dedicated preset. Before activation, the Host captures exact live parent registrations from the reviewed set; only first-party factory-owned definitions qualify. The original child manager must publish the reserved child under that exact parent before the grant attaches tools to the child's own scope. Every call uses the original ToolRuntime and tool executor; standard file tools retain the file observation policy and Android filesystem guard. App file access stays inside the canonical directory captured from the parent at activation. Writes also intersect both current sandbox modes and immutable permission roots; switching directories does not enlarge the parent's write permission. Parent visibility changes, registration replacement, policy downgrade, cancellation or retirement deny newly unauthorized calls. Calls already executing retain their original tool's cancellation and settlement behavior.

Children starting under read-only policy never acquire write tools from a later policy upgrade. Available web tools are inherited only from the parent's reviewed registrations and retain their providers' checks. The child receives neither App-UID Shell, PTC nor recursive delegation tools. Structured children can use the same authorized tools before submitting their own validated `structured_output`. Its exact definition, registration and executor are captured after original child setup; a later same-name replacement is denied. SAF grants and parent attachments are not delegated across Sessions: their current-session guards remain independent. Cold-resumed children reconstruct their Session history but receive no file, web or Linux grant from a preset name or persisted lineage alone.

`linux_exec` uses the child's private Session disk with no guest networking. Changes persist only when activation permitted writes and both current parent and child policies remain writable; otherwise command changes are discarded. Later policy upgrades cannot enlarge the activation grant. `linux_import` reads authorized App files and `linux_export` publishes a new App file; relative App paths resolve from the child cwd. Both transfers require initially writable activation and current parent/child write permission, and remain inside the activation directory and both permission roots. Policy is rechecked after asynchronous file preparation. Linux has one execution slot across the App, so parallel workflows must serialize Linux steps across children. A busy refusal occurs before native dispatch; it is neither completion nor grounds for automatic replay. Cancellation waits for native retirement and retains any returned commit receipt instead of assuming rollback.

Foreground calls publish only a confirmed completed receipt. `run_in_background: true` is admitted only by the App's explicit background policy and transfers the prepared request to `startBackgroundDsl`, preserving the parent and creating ToolCall IDs in the real jobs registry. The tool-step signal is not retained after handoff. Job cancellation and owner disposal remain the existing cancellation owners; failed or unconfirmed retirement never becomes a completed result or synthetic Session end.

Host checks: `node --import tsx --test apps/android/tool/tool-native-workflow.test.mjs apps/android/tool/tool-workflow-preflight.test.mjs apps/android/tool/workflow-child-tools.test.mjs apps/android/tool/workflow-subagent-backend.test.mjs`. The child suite loads the original tools through the real parent preset Loader, runs real child Agents and ToolRuntime calls against temporary files, verifies durable JSONL tool results, and checks policy downgrade, registration identity, protected metadata, directory changes, structured results, cancellation and cold resume. Model replies and web providers are fixtures. Linux cases use the real NativeLinuxVm host owner with fixture native receipts; they do not boot an Android guest. These checks establish neither public-network nor Android Binder execution. The other suites exercise the real jobs registry with the native boundary substituted. The original package regression is `node node_modules/vitest/vitest.mjs run packages/workflow/tool-workflow/tests/tool-workflow.spec.ts`.

For the remaining device proof, use a test-only composition inside the existing App process with a scripted model adapter and a fresh `android-…` Session, keeping user account settings unchanged. Run the actual ToolRuntime through foreground arithmetic, a real confined child, and a background job followed by `job_kill`; compare persisted Session events, native receipt identities and job outcomes. Only that reviewed composition may explicitly open the registration gate during acceptance. Kotlin-only transport fixtures or host substitutes cannot satisfy this end-to-end evidence requirement.
