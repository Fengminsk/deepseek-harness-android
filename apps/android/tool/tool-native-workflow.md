# Android native workflow registration

English | [中文](tool-native-workflow.zh.md)

`registerAndroidWorkflowTool` registers the original `workflow` parameter, result and presentation contract through `createWorkflowToolDefinition`. The App supplies the executor and a build-owned availability function; its default is closed. No profile value, model argument or user credential can open that gate. The production `index.mjs` integration and device acceptance are separate gates; importing this module alone registers nothing.

Each invocation captures the exact current ToolRuntime definition and registration identity, checks the live parent Agent and its real Session ID, and consumes one App-owned admission ticket. The App issues an ungranted DSL scope with a 120-second deadline, at most eight children and two concurrent children. The original JavaScript DSL runs through the fixed isolated guest, not in the Node host. Child tools use a separate Host grant; they do not give the DSL direct filesystem or network access.

Children retain the parent model route and dedicated preset. Before activation, the Host captures the exact live parent registrations for `read`, `glob`, `grep`, `write`, `edit`, `web_search` and `web_fetch`; only first-party factory-owned definitions qualify. The original child manager must publish the reserved child under that exact parent before the grant attaches tools to the child's own scope. Every call uses the original ToolRuntime, file observation policy, Android filesystem guard and tool executor. File access stays inside the canonical directory captured from the parent at activation. Writes also intersect both current sandbox modes and immutable permission roots; switching directories does not enlarge the parent's write permission. Parent visibility changes, registration replacement, policy downgrade, cancellation or retirement deny new calls. Calls already executing retain their original tool's cancellation and settlement behavior.

Children starting under read-only policy never acquire write tools from a later policy upgrade. Available web tools are inherited only from the parent's reviewed registrations and retain their providers' checks. The child receives neither Shell, Linux, PTC nor recursive delegation tools. Structured children can use the same authorized tools before submitting their own validated `structured_output`. Its exact definition, registration and executor are captured after original child setup; a later same-name replacement is denied. SAF grants and parent attachments are not delegated across Sessions: their current-session guards remain independent. Cold-resumed children reconstruct their Session history but receive no file or web grant from a preset name or persisted lineage alone.

Foreground calls publish only a confirmed completed receipt. `run_in_background: true` is admitted only by the App's explicit background policy and transfers the prepared request to `startBackgroundDsl`, preserving the parent and creating ToolCall IDs in the real jobs registry. The tool-step signal is not retained after handoff. Job cancellation and owner disposal remain the existing cancellation owners; failed or unconfirmed retirement never becomes a completed result or synthetic Session end.

Host checks: `node --import tsx --test apps/android/tool/tool-native-workflow.test.mjs apps/android/tool/tool-workflow-preflight.test.mjs apps/android/tool/workflow-child-tools.test.mjs apps/android/tool/workflow-subagent-backend.test.mjs`. The child suite loads the original tools through the real parent preset Loader, runs real child Agents and ToolRuntime calls against temporary files, verifies durable JSONL tool results, and checks policy downgrade, registration identity, protected metadata, directory changes, structured results, cancellation and cold resume. Model replies and web providers are fixtures; this establishes neither public-network nor Android Binder execution. The other suites exercise the real jobs registry with the native boundary substituted. The original package regression is `node node_modules/vitest/vitest.mjs run packages/workflow/tool-workflow/tests/tool-workflow.spec.ts`.

For the remaining device proof, use a test-only composition inside the existing App process with a scripted model adapter and a fresh `android-…` Session, keeping user account settings unchanged. Run the actual ToolRuntime through foreground arithmetic, a real confined child, and a background job followed by `job_kill`; compare persisted Session events, native receipt identities and job outcomes. Only that reviewed composition may explicitly open the registration gate during acceptance. Kotlin-only transport fixtures or host substitutes cannot satisfy this end-to-end evidence requirement.
