# App-owned isolated capability dispatch

English | [中文](isolated-capability-dispatch.zh.md)

`IsolatedCapabilityBinderDispatch` is an App-side transport seam for a future isolated PTC/workflow executor. It is not registered with the current diagnostic guest or the model-facing runtime. Programmatic tools remain unavailable until a guest script interpreter and its full confinement have been verified.

The owning App service creates one `IsolatedCapabilityJournal` for its lifetime and passes that same instance to each admitted session. Journal startup recovery must be inspected before admission; unfinished or uncertain runs are never replayed. The App selects the workspace root, immutable readable/writable policy, exact grant targets and actions, owner task ID, and a lease of at most five minutes. The guest receives only random grant IDs and actions, a run ID, and a per-run 256-bit nonce. It receives no file path, workspace root, credential, or Android `Context`.

The App binds a fresh non-exported isolated service for the session, sends one offer over that bound Messenger, and routes its reply Messenger to this dispatcher. The first HELLO pins the actual `Message.sendingUid` after matching the nonce, run ID and reported UID. Subsequent calls and FINISH require that same UID; an App-UID, mismatched UID, wrong run or nonce, unexpected Bundle key, concurrent call, or malformed request terminally fails the run. The reported UID cannot substitute for Binder's sender UID. Binder callbacks and each capability call run on dedicated background threads; factory admission, sendOffer, binding lifecycle and cancellation must also be invoked off the main thread because their audit paths can write to disk. Each call is limited to an App-issued grant ID and action, and is checked again by `IsolatedCapabilityBroker`. It consumes a one-use call ID before dispatch and durably records admission, outcome, and terminal state. File operations use `IsolatedCapabilityWorkspace`, whose opens and writes are anchored to the App-private root. FINISH only proposes a result and enters STOPPING; it never writes `COMPLETED`. The dispatcher sends STOPPING so the guest can exit. Only the bound Binder death followed by the App owner's successful binding cleanup commits `COMPLETED`. If death or cleanup is not confirmed before the absolute lease deadline, the run fails closed. Cancellation and unexpected worker death revoke the run; in-flight edits retain the broker's `COMMIT_UNCERTAIN` result when their commit cannot be proven.

This module does not itself bind a service, identify a ServiceConnection's UID independently, run scripts, broker network, or isolate the existing App-UID Shell and plugin tools. A production caller must own the ServiceConnection, pass a cleanup callback that releases the binding and stops the guest on cancellation or deadline, keep the journal alive, and close the dispatcher on cancellation or binding failure. The dispatcher runs cleanup off the main thread, observes the bound Binder's death, and has its own deadline timer that invokes cleanup if a guest ignores STOPPING. An ambiguous disconnect after FINISH waits only until the lease deadline and never confirms success by itself. Binder sender attribution, isolated UID allocation, App-private filesystem checks, process death, and real edit uncertainty require device acceptance before model-facing enablement.
