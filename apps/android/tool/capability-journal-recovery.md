# Capability journal recovery

`IsolatedCapabilityJournal` inspects at most 16 MiB of App-private JSONL when constructed and exposes that `startupReport()` even when it cannot admit another capability run. `inspect()` reads the current file without changing it. Each frame is limited to 2,048 bytes and must end with a newline. Invalid UTF-8, an unknown field or phase, a torn final frame, and a file over the size limit produce a damaged report. The App must not run or retry a capability call when this report requires inspection.

The report names an unfinished run, each `CALL_STARTED` without matching `CALL_SETTLED`, and each settled edit marked `COMMIT_UNCERTAIN` or `AUDIT_UNCERTAIN`. Edit reviews retain the expected revision and any recorded result revision. A terminal run record does not erase an in-flight call; a settled run with an uncertain edit still requires review. The report retains at most 4,096 call details and 4,096 run summaries, then marks truncation and blocks admission. Neither reading the report nor reopening the journal replays an edit or decides whether an incomplete edit committed.

The `:agent` Service constructs this journal before starting Node and retains its startup report. A failed inspection closes file-granted admission. Before consuming an App-approved file grant, `IsolatedRunNativeBridge` rechecks the same journal with `requireCleanAdmission()`: the startup report and current log must be complete, unchanged, under capacity, and free of unresolved runs. An active unfinished run also blocks a second file-granted admission. The App-only `runtime.capabilityAudit` method exposes bounded, read-only pages through **Background execution → File operation audit**. It shows unfinished and uncertain run/call facts, target paths, and recorded revisions; it never replays, deletes, or declares a write recovered. If inspection or pagination fails, the view withdraws stale facts and tells the user to inspect the actual workspace file before considering a retry. Cross-process writer coordination and device-level directory durability still require Android acceptance.

The writer refuses admissions after startup finds unresolved or damaged history, after its own write becomes uncertain, or when the 16 MiB file is full. `archiveSettled()` is an explicit maintenance operation: it only atomically renames a completely settled, unchanged journal to a unique App-private archive and syncs the directory. It never removes the archive or rotates incomplete history. Stop all owners and retain/export the archived file under an operator-defined retention policy; a full unresolved journal requires manual investigation, not automatic truncation. The reader is wired to App startup and file-granted native admission, but production PTC execution still has separate readiness gates.
