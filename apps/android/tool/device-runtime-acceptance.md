# Packaged Node tool acceptance

[中文](device-runtime-acceptance.zh.md)

`NativeRuntimeToolsAcceptanceInstrumentation` runs the packaged Android Node engine, ordinary `dsh --profile device-acceptance` launch, production AgentLoop, ToolRuntime, Session persistence, subagent/job services and native Binder owners. The AndroidTest assets contain the fixture profile and scripted model; none are registered by the product runtime. Standard invocations create a new `noBackup/native-runtime-acceptance/<uuid>` home, separate from user profiles, credentials and Sessions. Explicit PTC recovery resumes its own prepared home and Session, preserving the original fixture. Its callback transport uses the production workflow/PTC owners but is a narrow test carrier rather than the complete `AgentService` or UI startup path.

`all` includes only `workflow`, `ptc` and `linux`. Separate `ptc-process-death` and `ptc-saf` suites require their own prepared fixtures and are never added to `all` implicitly; see [PTC lifecycle acceptance](ptc-lifecycle-device.md) for their preparation, cleanup and evidence limits.

Build the App and AndroidTest together with `-PdshAcceptanceBuildType=release -Ptarget-platform=android-arm64`, install both with `adb install -r`, then force-stop the App before each instrumentation invocation so embedded Node starts in a fresh process. Run `adb shell am instrument -w -r -e suite workflow com.minnnng.dsh_android.test/com.minnnng.dsh_android.NativeRuntimeToolsAcceptanceInstrumentation`; use `ptc`, `linux` or `all` for the other cases. `INSTRUMENTATION_CODE: -1` and `passed: true` mean at least one named check executed and none failed; they do not mean complete acceptance. The retained fixture home contains only acceptance data and its runtime diagnostics.

Keep the acceptance page in the foreground throughout this fixture. Only the release acceptance build includes `RuntimeAcceptanceActivity`, a non-exported Activity in `:agent` with no launcher entry. `AcceptanceForegroundLease` requires an already unlocked, interactive device; it never wakes or unlocks it. Runtime preparation waits for a drawn, focused black window and a screenshot whose pixels are all RGB zero. The page hides system bars and uses the lowest window brightness without changing system settings. It keeps the screen on while visible and starts neither Flutter, `AgentService` nor the product Node profile. Loss of focus, visible system bars or System Back fails the fixture. Carrier cleanup closes the page. This foreground condition avoids relying on a cached background process being scheduled; it does not establish background execution or lock-screen survival.

Run `BlackScreenAcceptanceInstrumentation` to sample the composed display six times over thirty seconds, including system bars. It saves dimensions and the result, not screenshots. Device evidence is required before claiming black-screen protection works on a particular phone. The black Activity shares the Agent process: killing that process, force-stopping the package or installing an update removes the window. Do not run those disruptive tests under an uninterrupted-black-screen requirement until a separate screen-protection arrangement covers the transition. Normal cleanup also removes the window; the host operator must put the display to sleep when testing ends.

A 120-second startup watchdog runs until fixture Node dispatch. On timeout it publishes `startup-timeout` and the current startup phase before requesting a stack trace on a separate daemon thread; the carrier waits at most two seconds for that trace, then reports failure with cleanup unconfirmed. A timeout prevents a queued worker from dispatching Node later. The watchdog itself cannot execute while the whole process is frozen, so missing timeout output does not establish progress. These startup diagnostics are separate from the suite execution limits below.

The result separately reports `complete` and `coverage.required`, `coverage.passed`, `coverage.failed`, `coverage.unverified`, and `coverage.issues`. Check names are qualified by suite. The [report aggregator](device-runtime-acceptance/report.mjs) owns the required names; missing checks remain unverified even if their suite omits them. `complete: true` requires every check for the selected suite, or every suite for `all`, to pass without unresolved gaps, missing evidence, duplicate results or unknown names/statuses. Unknown suites and zero executed checks return both `passed: false` and `complete: false`. Raw suite reports remain available. This completeness applies only to this fixture's declared checks, not production service lifecycle or the overall Android delivery. `node --test apps/android/tool/device-runtime-acceptance-report.test.mjs` validates aggregation without a device.

Workflow checks execute model-shaped requests through the real ToolRuntime, assert native compute and child results, cancel a genuinely entered scripted child through `job_kill`, and compare durable workflow Session start/end records with native recovery observations. These three checks deliberately use children without tools; the Linux suite owns the working child check. Scripted models have no credentials or external model requests. PTC checks use the production reviewed SDK for local reads, guarded writes/edits and attachment materialization, isolated UIDs, callbacks, cancellation and CPU limits; public web fetch is a real network check. The SAF case requires the persisted acceptance-directory grant and the unchanged `dsh-saf-acceptance.txt` fixture with its recorded hash. The attachment cases create their own files in their own Session. User documents and existing session attachments are not inspected.

The `linux` suite requires an [Alpine acceptance build](tinyemu-build.md#alpine-acceptance-apk) with its matching release AndroidTest APK. It uses a dedicated `.device-acceptance-<uuid>` child of the production App workspace and tests Linux execution and persistence, file import/export hashes, no-overwrite publication and read-only policy. Its working child check invokes the native `workflow` tool, creates a real child Agent, and sends scripted `linux_import`, `linux_exec` and `linux_export` model calls. The original ToolRuntime, first-party grants, NativeLinuxVm and Android Binder owners execute the work. Assertions compare child and parent identities, inherited registrations, native completion/retirement, exported bytes and hashes, persisted child tool results and Linux receipts, and the native workflow's retired child record. The separate acceptance home retains Session evidence. This check covers a successful writable child; it does not certify child policy revocation or cold recovery.

`production-python-stdlib-file-analysis` calls the production `linux_exec` tool to execute [the Python fixture](device-runtime-acceptance/python-analysis.py) in Alpine. It creates three small UTF-8 files and JSON metadata, writes and reads a deflated ZIP, commits and reopens SQLite for integrity and grouped byte-count checks, calculates SHA-256, and launches a second Python process to independently read the ZIP. It also creates an SSL context with hostname/certificate verification and installed trust anchors; no TLS connection is attempted. Node compares the output with independently computed expected files, sizes and hashes and requires Linux/RISC-V identity plus the normal isolated-UID completion/retirement receipt. The AndroidTest asset directory includes both `python-analysis.py` and its `.mjs` helper, and instrumentation copies both into its fixture home. `node --test apps/android/tool/device-runtime-acceptance-python.test.mjs` runs the exact script with the host Python and checks malformed-input failure and output validation; this is script validation, not Android evidence. Coverage is limited to the delivered standard-library operations, not pandas, NumPy, pip or other third-party packages. Guest networking and process-death import recovery remain named unverified checks.

Workflow and Linux suites share one callback/preset owner for an invocation, including `all`, and close it before reporting success. Run suites separately for clearer failure evidence. The workflow and PTC carrier waits remain 240 seconds each. Linux permits eleven serialized guest boots—eight parent and three child operations—at the existing 120-second command limit plus 30 seconds of retirement allowance each, with 120 seconds of carrier margin: 1,770 seconds total. `all` adds the two 240-second suite allowances, totaling 2,250 seconds. These are bounded test-carrier waits, not expected durations or extensions of product limits; the child workflow still has the production 120-second overall deadline. A carrier timeout is reported as a failure and cannot establish which unfinished check completed.

`node apps/android/tool/check-device-runtime-profile.mjs` is only a host startup smoke check: it launches the same profile and stops when the first production native admission request appears. It cannot certify device execution. Product capability gates stay closed until their corresponding full device checks pass.

For a separate production-service recovery check, run `node apps/android/tool/acceptance-agent-service-recovery-device.mjs --serial <device> --accept-network-toggle-and-lock` with the matched release test APK installed. This starts the real `AgentService`, creates one dedicated Session without calling a model, and checks the same runtime generation, Agent process and Session event hash while the phone is locked/offline and after connectivity is restored. It temporarily disables Wi-Fi and mobile data, then restores both original flags and the original display on/off state in `finally`. It does not change VPN settings or unlock the keyguard. The dedicated Session is archived on success. A pass proves service and durable Session availability, not survival of an active model request or its network retry.
