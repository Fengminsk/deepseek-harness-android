# Packaged Node tool acceptance

[中文](device-runtime-acceptance.zh.md)

`NativeRuntimeToolsAcceptanceInstrumentation` runs the packaged Android Node engine, ordinary `dsh --profile device-acceptance` launch, production AgentLoop, ToolRuntime, Session persistence, subagent/job services and native Binder owners. The AndroidTest assets contain the fixture profile and scripted model; none are registered by the product runtime. Each invocation creates a new `noBackup/native-runtime-acceptance/<uuid>` home, separate from user profiles, credentials and Sessions. Its callback transport uses the production workflow/PTC owners but is a narrow test carrier rather than the complete `AgentService` or UI startup path.

Build the App and AndroidTest together with `-PdshAcceptanceBuildType=release -Ptarget-platform=android-arm64`, install both with `adb install -r`, then force-stop the App before each instrumentation invocation so embedded Node starts in a fresh process. Run `adb shell am instrument -w -r -e suite workflow com.minnnng.dsh_android.test/com.minnnng.dsh_android.NativeRuntimeToolsAcceptanceInstrumentation`; use `ptc` or `all` for the other cases. A pass requires `INSTRUMENTATION_CODE: -1` and a result with `passed: true`; each nested check marked `unverified` remains an evidence gap. The retained fixture home contains only acceptance data and its runtime diagnostics.

Workflow checks execute model-shaped requests through the real ToolRuntime, assert native compute and child results, cancel a genuinely entered scripted child through `job_kill`, and compare durable workflow Session start/end records with native recovery observations. Child models have no credentials or external network requests. PTC checks use the production read-only SDK, actual local fixture reads, isolated UIDs, callbacks, cancellation and CPU limits; public web fetch is a real network check. The SAF case reads only the explicitly staged acceptance file and verifies its hash; the attachment case creates its own ZIP in its own Session. User documents and existing session attachments are not inspected.

The `linux` suite additionally requires a build containing the verified Linux fixture. It uses a dedicated `.device-acceptance-<uuid>` child of the production App workspace, tests Linux execution and persistence, file import/export hashes, no-overwrite publication and read-only policy. The ordinary DSH home is still separate. These checks do not certify Python or a complete distribution image.

`node apps/android/tool/check-device-runtime-profile.mjs` is only a host startup smoke check: it launches the same profile and stops when the first production native admission request appears. It cannot certify device execution. Product capability gates stay closed until their corresponding full device checks pass.

For a separate production-service recovery check, run `node apps/android/tool/acceptance-agent-service-recovery-device.mjs --serial <device> --accept-network-toggle-and-lock` with the matched release test APK installed. This starts the real `AgentService`, creates one dedicated Session without calling a model, and checks the same runtime generation, Agent process and Session event hash while the phone is locked/offline and after connectivity is restored. It temporarily disables Wi-Fi and mobile data, then restores both original flags and the original display on/off state in `finally`. It does not change VPN settings or unlock the keyguard. The dedicated Session is archived on success. A pass proves service and durable Session availability, not survival of an active model request or its network retry.
