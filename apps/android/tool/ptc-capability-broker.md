# Android isolated capability broker

For post-crash audit and capacity maintenance, see [capability journal recovery](capability-journal-recovery.md). The `:agent` Service inspects the App-private journal on startup and denies file-granted runs when the audit is unavailable or unresolved. This is host wiring, not device acceptance.

The App process owns one `IsolatedCapabilityBroker` per proposed PTC or workflow run, tied to an opaque task ID in its private audit journal. It issues a random run ID and up to 32 random grant handles. Each App-only `GrantSpec` names one relative text file or a named subdirectory ending in `/` inside an App-private workspace and selects `READ`, `SEARCH`, `EDIT`, and/or `WRITE`. The guest receives opaque handles in issuance order; it cannot select an App workspace root, credential, network endpoint, shell, or unregistered tool. For an internally constructed directory grant only, a call must include a relative child path such as `sub/file.txt`. Exact-file calls reject that field. The broker checks the joined workspace-relative target again against the readable/writable policy and audits that exact target.

A guest call carries `{runId, callId, grantId, action, boundedArgs}`. The App validates every ID and the live monotonic lease, records admission to an App-private fsynced JSONL journal, performs only the granted operation, records settlement, then replies. A call ID is consumed before dispatch and a replay cannot perform a second edit. Rejections are logged too. The broker caps a run at 128 calls and five minutes. A failed journal write denies new work. A lost settlement yields `AUDIT_UNCERTAIN`; the App must inspect the workspace rather than retry an edit blindly.

`IsolatedCapabilityWorkspace` implements the binding with the existing secure directory writeback. Reads return UTF-8 text and a SHA-256 revision, capped at 64 KiB. Search returns a bounded list of locations and previews. `EDIT` performs literal replacement; `WRITE` publishes complete bounded UTF-8 text. Both require an exact writable grant and an expected SHA-256 revision. `WRITE` with `missing` creates only an absent file. A changed revision is `STALE`; both stage, sync, and atomically rename within the anchored workspace directory. The writer rejects `.git`, `.agents`, `.codex`, and `.aws` path segments even if a caller bypasses the broker. On the production provider it fails closed when it cannot verify that an existing target has exactly one hard link. Cancellation, expiry, and guest death close the run exactly once. If either write might have committed while a terminal signal arrived, its result is `COMMIT_UNCERTAIN`, never clean success. The journal records grant targets only in the App-private file; guest-facing handles contain no filenames.

This directory call protocol is an internal, fail-closed subset, not a general writable-root feature. `IsolatedRunNativeBridge` still rejects all directory grants at admission. Link-count checks and anchored basic attributes do not establish a complete guarantee against a hostile same-App-UID writer racing a named path. There is no directory listing or directory creation operation. Child names reject traversal, absolute paths, similar-prefix roots, controls, excessive depth and size; operations retain SHA-256 revision checks, call budgets, cancellation and the durable audit. Host tests verify broker routing and rejection, not Android provider behavior. Do not loosen native admission until same-UID race assumptions and device checks have been resolved.

This is a host binding contract, not a PTC executor. The Android profile still disables original Node PTC and workflow scripts. A guest engine that admits arbitrary Node filesystem/subprocess/network calls would bypass these handles and is not approved. A device run must verify Android's secure directory provider, UID separation, Binder death, concurrent edits, offline execution, and restart recovery before claiming the feature works on a phone. A hostile same-App-UID writer remains outside the current writeback guarantee; see [confinement notes](ptc-workflow-confinement.md).

The production writer requires `Files.newDirectoryStream` to yield `SecureDirectoryStream`; otherwise it denies `READ`, `EDIT`, and `WRITE` rather than falling back to a pathname-based open. Android's [AOSP secure directory stream implementation](https://android.googlesource.com/platform/prebuilts/fullsdk/sources/+/refs/heads/androidx-transition-release/android-34/sun/nio/fs/UnixSecureDirectoryStream.java) and [Unix `nlink` view](https://android.googlesource.com/platform/prebuilts/fullsdk/sources/+/refs/heads/androidx-constraintlayout-release/android-35/sun/nio/fs/UnixFileAttributeViews.java) show the intended provider mechanisms, but do not establish behavior on this device or vendor filesystem. Those checks and existing read/edit compatibility remain device acceptance work.

The independent `FileBrokerProviderInstrumentation` exercises the actual App-private Android provider in `:agent`, including secure stream type, `unix:nlink`, versioned `READ`/`EDIT`/`WRITE`, stale revision rejection, cancellation, and symbolic/hard-link isolation. It uses only temporary files under the test App's private `filesDir` and removes them afterward. Its offline parser check is `node --test apps/android/tool/acceptance-file-broker-provider-device.test.mjs`; after building the exact App and AndroidTest APKs, run `node apps/android/tool/acceptance-file-broker-provider-device.mjs --apk <app.apk> --test-apk <androidTest.apk> --preflight-only` to verify artifact identities and Agent-process registration without touching the phone. Once phone use is authorized, omit `--preflight-only` and select the device with `--serial`; `--allow-existing` explicitly permits replacing an already installed App. A passing offline test or APK preflight is not device acceptance. Do not report the broker usable on a phone until the instrumentation passes there and the remaining UID, restart, and concurrency boundaries are checked.
