# Android execution sandbox policy: writable paths and network

English | [中文](android-sandbox-policy-design.zh.md)

## Decision and current boundary

Adopt a **Codex-style, policy-governed execution world** for future Android PTC and workflow scripts: a separate isolated guest, explicit read and write grants, an independently controlled network capability, and App-side approval before effects. This is an implementation design, **not an enabled model-facing feature**. The Android profile still disables `ptc-runtime`, `workflow-ptc`, `tool-workflow`, and `preset-ptc`; the [execution gates](ptc-execution-design.md) remain mandatory. The isolated V8 guest has internal, policy-leased [file calls](ptc-capability-broker.md) and [exact-host HTTPS calls](isolated-network-broker.md), durable admission, and a one-run App review queue. No production model request producer invokes it, and device confinement remains unverified.

Do not equate this proposal with the current DSH `sandbox-policy`: its `read-only`, `workspace-write`, and `danger-full-access` modes govern **file effects only**. The original Node PTC provider can directly use Node filesystem, network, and subprocess APIs within the chosen OS runner's constraints. Its Android runner is absent. In the Android profile, `sandbox-policy.mode` currently defaults to `workspace-write` for the existing file-tool provider. `android_shell` is closed to ordinary model calls; an explicitly enabled internal migration mode executes with the App UID after one-call approval and has **no OS workspace confinement**. No policy UI label may imply otherwise. See the original [policy](../../../packages/sandbox/sandbox-policy/README.md), [Node PTC provider](../../../packages/ptc-runtime/ptc-runtime-node/README.md), and [Android profile](../runtime/cordis.patch.yml).

The proposed boundary applies to the built-in isolated script guest only. It does not constrain trusted App code, App-UID Shell commands, third-party plugins loaded into the Host, executable configuration, or plugin installation scripts; those require separate policy and trust decisions. The App must not call the whole product "sandboxed" merely because one guest is isolated.

The analogy is about **separate controls**, not reusing Codex internals. Official Codex documentation distinguishes writable roots, approval policy, and command network access; its workspace-write default keeps network off unless enabled, and network destination rules require their own enforcement. OpenAI's sandbox guidance keeps credentials and approvals in a trusted harness, outside model-directed compute. Android's `isolatedProcess` gives a separate UID with no permissions of its own, but does not by itself provide a selected-workspace filesystem or HTTP policy. [Codex approvals and sandbox](https://learn.chatgpt.com/docs/agent-approvals-security), [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference), [OpenAI sandbox security](https://developers.openai.com/api/docs/guides/agents-api/environments/security), [Android Service reference](https://developer.android.com/guide/topics/manifest/service-element).

## Proposed policy contract

| Dimension | Initial state for a new script run | User-controlled extension | Non-bypassable boundary |
| --- | --- | --- | --- |
| File reads | Only explicitly attached workspace or file grants; no App home, account store, private cache, arbitrary SAF URI, or other App-private data | User selects a document/tree through the system picker or an existing authorized workspace | Guest gets opaque handles and bounded bytes, never a raw App path or ambient `ContentResolver` |
| File writes | `read-only` for newly admitted PTC/workflow scripts | `workspace-write` for an explicit, named workspace; one outside file only through a fresh, exact SAF grant and per-call approval | Broker enforces relative name, open parent identity, expected revision, size/quota and atomic publication; no implicit temp root outside that workspace |
| Network | `off` for guest code; trusted model transport and App account traffic remain separate | `restricted` exact HTTPS destination hosts for an approved task/lease, with an explicit one-call prompt when needed | No direct guest socket API; only an App-side bounded HTTP broker with URL/redirect/DNS/IP validation; no credential exposure |
| Processes | No direct shell, native subprocess, dynamic library, local server, or package installation inside a script | None in the first release; a later isolated process provider requires its own proved confinement | `android_shell` remains a separate, explicitly labelled App-UID tool; its approval must never be treated as PTC sandbox enforcement |
| Approval | Deny an effect outside the standing grant, or suspend before it | User authorizes the exact target/action once or updates a named session policy | Approval issues a narrow broker grant; it never switches a model program to the App UID or `danger-full-access` |

The `read-only` proposal applies **only to the new model-authored script executor**; it does not silently change existing Android file tools, which currently use the DSH `workspace-write` policy. A user-authorized session workspace may start subsequent scripts in `workspace-write` after an explicit trust choice, matching the useful Codex editing flow. A policy downgrade applies to the next call and revokes old write grants; in-flight mutations must settle or become `COMMIT_UNCERTAIN` before the new policy is reported. The mobile UI should show the effective file mode, named workspace, network mode/hosts, and whether Shell is outside this sandbox. Do not offer `danger-full-access` for Android guest code.

### Admission and authority

For each run, the trusted App freezes `{sessionId, ownerId, workspaceId, workspaceRevision, fileMode, readableGrantIds, writableRootId?, networkMode, exactHosts, expiry, budgets, policyVersion}` and records it before binding the isolated guest. The guest receives only a run ID and opaque handles. Every callback checks the live run, owner, lease, capability, action, and policy version. A child Agent/workflow phase inherits **at most** the parent's grants and budget; delegation cannot broaden files or hosts. An approval after admission creates a new, single-use capability for the suspended call, not a retroactive rewrite of prior decisions. Cancel, timeout, Binder death, owner disposal, or process death revokes capabilities and settles the journal once. An offline run cannot acquire a fresh network grant or fake approval; it can still complete authorized local work within its deadline.

The existing file broker's five-minute lease is a safety cap for that prototype, **not** the original workflow lifetime contract: the original workflow adapter can request no overall PTC deadline. A long-running Android workflow needs a trusted-owner lease renewal and durable child accounting design, or an explicitly documented product limit. Do not silently terminate or silently extend a workflow to claim parity.

The workspace root is an App-resolved identity, not a guest-provided string. An App-private workspace can be bridged through descriptor-anchored relative operations; a SAF tree remains a URI-backed capability, not a local pathname. Persisted SAF permission can disappear when the document is moved or deleted, so each call must revalidate access and fail closed. Do not request broad `MANAGE_EXTERNAL_STORAGE` for this design. The Android picker supplies user-controlled grants and has directory restrictions on Android 11+. [Android Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files).

The first write surface is create/replace/edit of regular files in an authorized workspace. Deny deletion, moving whole directories, permission changes, path traversal, symlinks, hard-link aliases, device nodes, and writes to App runtime/credential directories until each has a separate design and tests. Before replacing existing content, require its recorded revision, cap bytes and files per run, stage in the same opened directory, sync, publish, and retain a bounded undo/version record. A stale or uncertain commit is **not** automatically retried. The existing secure-directory writeback has documented same-UID races; do not claim adversarial same-UID safety from it. The isolated guest should not share the App UID, which removes the model program from that race class, while the trusted broker still needs concurrency controls and device tests. [Confinement notes](ptc-workflow-confinement.md).

Network policy is **not** a boolean permission to open arbitrary sockets. `off` denies model-originated HTTP. `restricted` permits exact normalized HTTPS hostnames only; each redirect target is checked again, and connection IP checks reject loopback, link-local, private/reserved destinations unless a separate explicit local-network feature is designed. Deny URL userinfo, non-HTTPS schemes, literal IP destinations, arbitrary ports, proxy tunnelling, WebSocket upgrades, and ambient cookies by default. Re-resolve or pin the validated address at connection time to avoid DNS rebinding; cap request/response bytes, redirects, concurrency and elapsed time. The App can use its own model/account network separately, but model programs receive neither API keys nor raw responses that disclose tokens. A trusted network broker, not the guest, enforces the host list. OpenAI's hosted sandbox offers `disabled`, `restricted` exact-host, and `enabled` network modes; this Android policy deliberately omits unrestricted guest access. [OpenAI-hosted sandbox network settings](https://developers.openai.com/api/docs/guides/agents-api/environments/openai-hosted).

### Approval and failure behavior

The approval UI shows one human-readable request: operation, selected file/workspace or exact host, why it is needed, size/side effect, run identity, and `Allow once` / `Deny`. For a workspace policy change it may offer an explicit persistent session choice, but never bury it in a JSON editor. An expired, unavailable, or stale UI request denies the call. Store approval and execution as separate durable events; if execution or audit commit becomes uncertain, do not replay automatically. Read-only policy denial may be followed by a scoped approval request only for a concrete operation, and the original run resumes from its suspended call after the decision. This mirrors the separation of sandbox and approval in Codex without claiming Codex Auto-review applies to this App. [Codex approvals](https://learn.chatgpt.com/docs/agent-approvals-security), [OpenAI guardrails](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals).

Return structured `POLICY_DENIED`, `APPROVAL_DENIED`, `GRANT_REVOKED`, `SANDBOX_UNAVAILABLE`, `STALE_REVISION`, `NETWORK_DENIED`, `NETWORK_OFFLINE`, `COMMIT_UNCERTAIN`, or `AUDIT_UNCERTAIN` as appropriate. `offline` is an environment fact, not a reason to widen the host list. The UI must distinguish a genuine denial, no connectivity, an unavailable sandbox, and an unknown side effect. Never transform a failed isolated bind into App-UID execution.

## Existing model file tools and relative paths

The current Android model-file guard is separate from the isolated-script broker. It admits the original `read`, `read_image`, `edit`, `present`, `glob`, `grep`, and `str_replace_editor` for workspace-confined targets; relative paths resolve from the pinned Session working directory. `write` also uses the original `SandboxedFileSystem` mutation policy. The original string editor itself requires an absolute path. Its **directory** `view` remains denied: in a real ToolRuntime test the original two-level directory listing followed a child junction back to App home and disclosed `account.sqlite` by name. File `view` remains available. The original read/image tools require regular files, and `present` requires an existing regular file; those tools do not recursively list a directory. Bundled Windows ripgrep did not follow a child junction during a workspace-rooted `glob`/`grep` host test, but Android execution remains unverified.

The provider now resolves model targets against the pinned Session working directory at each stat/read operation, including when a lazy text stream is consumed. The guarded ripgrep subprocess seam also checks its launch cwd and search root. These checks reject a retained target whose parent was already redirected and a later Session cwd change. Model-scope directory enumeration stays closed because the original string editor follows child symlinks; reopening it requires confinement of every descendant and bounded traversal. A true race-resistant boundary would use directory handles and relative `openat`-style operations; pathname realpath checks still leave a same-UID symlink replacement window between validation and the system call. Do not describe the current guard as an OS sandbox or as protection against App-UID Shell, plugins, or future tools without this guard.

## Implementation order and acceptance

1. **Policy owner and UI.** Add an Android-specific policy record beside the original per-session file mode; versioned admission, readable/writable workspace IDs, network mode and exact hosts. Reconcile it durably after process death; show the effective policy and Shell exception without falsely advertising PTC availability.
2. **File broker integration.** Bind a real script engine to the existing broker, extend single-file grants to an App-resolved workspace tree with descriptor/SAF operations, keep journal review blocking on unresolved edits, and test grant inheritance, revocation and version changes. Do not enable the tool yet.
3. **HTTP broker.** Add the separate URL policy and request limits, deny direct guest networking, and test redirects, DNS changes, local IPs, oversized bodies, timeouts, offline and cancelled calls. Do not pass account credentials to the guest.
4. **Execution and workflows.** Implement the promised script syntax/bindings and child-agent lifecycle, or expose a clearly different restricted-tool provider; compare its behavior against original PTC/workflow tests. Do not advertise direct-Node parity from a V8-only engine.
5. **Device proof.** On a normal non-rooted device, show the isolated UID, denied App-private/out-of-grant file and network access from actual model-authored code, allowed revision-checked edits and allowlisted HTTPS, no unauthorized late side effects after kill/cancel, process-tree retirement, offline and APK-upgrade recovery. Capture policy and outcome in Session records. Only then consider enabling the model-visible tool.

Host unit tests and APK compilation cannot prove Android UID/SAF/Binder/network confinement. Until the device gates pass, existing file tools retain their explicit policy, `android_shell` stays closed to ordinary model calls; internal diagnostic mode requires explicit enablement and per-call approval, and PTC/workflow remain disabled. No root, ADB-device-control, global filesystem mount or hidden full-access fallback is part of this design.
