# Android isolated guest echo diagnostic

English | [中文](guest-echo-diagnostic.zh.md)

This reference describes the narrow `diagnostic.echo` Binder exercise implemented by [`IsolatedGuestBackend`](../android/app/src/main/kotlin/com/minnnng/dsh_android/IsolatedGuestBackend.kt) and [`IsolatedGuestService`](../android/app/src/main/kotlin/com/minnnng/dsh_android/IsolatedGuestService.kt). It is not a JavaScript or Workflow executor, does not run model-authored text, and is not connected to the disabled `ptc-runtime`, `workflow-ptc`, or `tool-workflow` modules.

The App validates a canonical JSON request containing exactly `version: 1`, `binding: "diagnostic.echo"`, and one `input.text` string. The complete frame is at most 8 KiB and the UTF-8 text at most 4 KiB; unknown bindings, fields, encodings, malformed Unicode, and extra bytes are rejected by [`GuestEchoFrame`](../android/app/src/main/java/com/minnnng/dsh_android/GuestEchoFrame.java). The App sends only this request identifier and frame to a non-exported `isolatedProcess` service. The guest asks the App for its one allowlisted echo callback; the App checks the Binder sender UID, the request and call identifiers, a single-call limit, and the echoed text before accepting the final frame. No path, file descriptor, account token, credential service, or ambient Node environment crosses this diagnostic interface. The broker message names a fixed binding rather than passing arbitrary operation names to the host.

Each request has one terminal outcome: `COMPLETED`, `CANCELLED`, `TIMED_OUT`, `WORKER_DIED`, or `ERROR`. The App admits only the first outcome; cancellation or timeout sends a cancel message and releases its binding. Android 10 and later use a distinct named isolated-service instance per request; Android 9 uses the platform's shared isolated-service binding. No script or subprocess runs in either case. Host Java checks cover canonical input admission and terminal-result races; they do not establish Binder UID enforcement, process death, or service teardown on a device.

The protocol reserves a versioned binding field so future host callbacks can be designed against original Workflow operations such as `begin`, `startChild`, `childResult`, `disposeChild`, and progress reporting. These operations are not accepted by the current parser. Enabling general PTC requires a separately reviewed script engine, explicit file/tool brokers, approval and logging, process and descendant termination, and device evidence described in [PTC and Workflow confinement](ptc-workflow-confinement.md).
