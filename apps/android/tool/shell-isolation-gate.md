# Android Shell isolation gate

English | [中文](shell-isolation-gate.zh.md)

The legacy `android_shell` path launches `/system/bin/sh` through an App-UID native supervisor after approval for each invocation. The shared DSH `AndroidShell` executor also runs in the App UID when explicitly enabled. Neither the working directory nor the original file-tool sandbox policy confines either Shell's filesystem or network effects.

`runtime/shell-execution-policy.mjs` now defaults to `isolated-required` when the process mode is unset. Since a general isolated Shell executor is unavailable, the model-visible `android_shell` tool is not registered and the shared `AndroidShell` entry refuses execution before spawn. An unknown mode also fails closed. The old approved App-UID Shell is reachable only when an internal migration or diagnostic process explicitly sets `DSH_ANDROID_SHELL_EXECUTION_MODE=app-uid-approved`; focused legacy fixtures set it themselves. This process-local switch is not a user-facing setting or a security sandbox. Code already executing in the App-UID Node process can call `fs`, `net`, or `child_process` outside these entry points, and the environment variable cannot defend against such code. Stage-4 general Shell functionality is temporarily unavailable by default while true OS confinement is implemented and verified.

Moving only `/system/bin/sh` to an `isolatedProcess` does not achieve a Codex-style writable-root/network policy: the Node host retains the App UID and ambient APIs, while an isolated UID cannot directly use the App-private working directory. [Android's Service reference](https://developer.android.com/guide/topics/manifest/service-element#isolatedProcess) specifies that an isolated service has no permissions of its own and communicates through the Service API. A real isolated Shell would require App-owned policy admission, descriptor- or broker-mediated file operations, separate network enforcement, durable approval/outcome accounting, and device proof that commands cannot escape those controls. Until then, do not label App-UID Shell or the product as sandboxed. Host regression: `node --test apps/android/tool/tool-android-shell.test.mjs apps/android/tool/shell-execution-policy.test.mjs apps/android/tool/shell-deadline.test.mjs`.

## Fixed-command device gate

`IsolatedShellProbe` remains an internal diagnostic, with no caller-supplied script, working directory, file descriptor, or network endpoint. The App binds a unique isolated Service instance, admits only its own UID and a UUID request, and waits at most five seconds. Its child receives an empty environment except `PATH=/system/bin`, starts from `/`, has a 1.5-second deadline and a 256-byte output ceiling. The Service drains output concurrently with execution so a full pipe cannot block its deadline. The child must report its own UID, fail to list the App-private directory, and fail to create one new UUID-named file there. The Service also attempts a direct Internet socket from its isolated UID. The App checks the Binder sender UID, reported UID, exact child output, and absence of the marker, then removes only that marker if an isolation failure created it. Cancellation and binding death fail closed.

Run the existing instrumentation `phase=shell-probe` on an unlocked, non-rooted Android device. A host unit test or APK build cannot establish that the child had a distinct UID or that the device denied the file/socket operations. This probe does **not** authorize model Shell: it neither supplies a workspace write broker nor an exact-host network broker. The existing native Shell supervisor requires its launcher to create a separate session/process group; the Kotlin probe does not meet that contract, so a general Shell runner also still needs independently verified whole-process-tree retirement before it can accept arbitrary commands. [Android isolated Service](https://developer.android.com/guide/topics/manifest/service-element#isolatedProcess), [Android named isolated binding](https://developer.android.com/reference/android/content/Context#bindIsolatedService(android.content.Intent,int,java.lang.String,java.util.concurrent.Executor,android.content.ServiceConnection)), [Codex sandbox and approvals](https://learn.chatgpt.com/docs/agent-approvals-security).

The pure evidence gate runs on a host JDK without Android/JUnit dependencies: `node apps/android/tool/acceptance-shell-probe.mjs` from the repository root.
