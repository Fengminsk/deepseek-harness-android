# 配对二维码：三条路线评估 + 终端字符画过渡实现

状态：2026-11-16。读者：决定 P6 配对体验投入的 lead、后续做 PC 侧界面或 App 扫码的同学。
相关：[reachability.md](reachability.md)（外网接入与安全边界）、[HANDOFF.md](HANDOFF.md) §4/§7、[protocol.md](protocol.md) §1.1/§2。

**结论先行**：

1. 现在只有「粘贴链接」一条路（`apps/android/lib/remote_pairing_page.dart:131-194`），而链接固定是 `wss://host:port#instance=<64 hex>&token=<43 base64url>`，手抄 107 个字符不现实。
2. 三条候选路线里，**长期唯一正确解是 ①「App 内扫码」**（相机 + 解码，一步到位）；②「PC 侧配对界面」只是 ① 的展示端，单独做不能缩短配对链路；③「短码手输」要改协议与信任模型，不做。
3. 本轮已落一个**零依赖过渡**：宿主在真终端里打印字符画二维码（`apps/remote-host/src/index.ts:568`、`:1645-1662`），手机用「能复制原文的扫码工具」扫出链接再粘贴。矩阵正确性由 `apps/remote-host/scripts/qr-selfcheck.ts` 证明（16/16，含与 App 同款 `qr 3.0.2` 的逐模块一致性与 Reed-Solomon 独立回读）。**本轮未做真机扫码验收**，清单见 §4。

## 1. 三条路线

### 1.1 路线 ①：App 内扫码（推荐，长期方案）

要做什么：

- 在 `apps/android/lib/remote_pairing_page.dart` 增加「扫描二维码」入口：相机预览 → 解码 → 交给现有 `RemotePairingFlow.pair(link, …)`（解析、取 CA、指纹校验、换令牌、落存储已经完全就绪，`apps/android/lib/remote_pairing_flow.dart:59-106`）。
- 依赖选择（**需要 lead 批准后才能 `flutter pub get`**，本轮不动 pubspec）：
  - `mobile_scanner`：Android 侧用 ML Kit，集成最省事；代价是 APK 体积增加（ML Kit 条码模块通常 1–3 MB 级别）与首次运行的模型下载行为（取决于配置）。
  - `google_mlkit_barcode_scanning` + `camera`：更可控，但要自己接相机生命周期与预览。
  - 纯 Dart 解码（`zxing2` 之类）+ `camera`：无原生模型、体积小，但解码速度与低光鲁棒性不如 ML Kit，需要自己实现取帧。
- 权限与交互：相机权限（`CAMERA` + 运行时请求）、拒绝时给可操作文案、扫码页要有「改用粘贴」兜底。
- 现有工程约束：App 已自带 `qr_flutter`（**只做编码渲染**，用在 Web 访问页：`apps/android/lib/settings.dart:5`、`apps/android/lib/settings.dart:686`），**没有任何解码依赖**，所以要新增一个。

成本与风险：

| 项 | 估计 |
|---|---|
| 代码量 | 扫码页 ~200–300 行 + 配对页入口 + 单测（可用假解码器注入，参考 `remote_pairing_flow.dart` 的注入风格） |
| 工期 | 1–2 天（依赖可用、不踩相机兼容问题） |
| 风险 | 新增原生依赖要 `pnpm install`/`pub get`（本轮禁止）、APK 体积、Android 11 真机相机兼容、权限弹窗文案 |
| 收益 | 配对从「复制粘贴」变成一步；对 PC 终端二维码、未来 PC 配对界面都通用 |

结论：**这是唯一值得投入的方向**，建议作为下一个 P6 批次，等 lead 批准依赖。

### 1.2 路线 ②：PC 侧配对界面显示二维码

现状：宿主已经有配对窗口的服务入口 `remoteHost.pair()`（`apps/remote-host/src/index.ts:300-301`、`:401-405`），但**没有任何 PC 侧界面**消费它（HANDOFF §4 第 6 项）。

关键判断：**单独做 ② 不能解决手机输入问题**。PC 屏幕上放一张二维码，最终还是要手机去扫；没有 ① 的扫码能力，手机只能靠系统相机/扫码 App「识别后复制文本」——这正是本轮终端方案已经达到的体验，所以 ② 的增量价值是「展示位置更正式 + 可以被远程/截图分享」，不是「配对链路更短」。

如果要 ②，真正的工作量在 PC UI（桌面 App 或 Web 页面），二维码编码部分本轮已经具备：`pairingQrMatrix()` 给出模块矩阵、`renderPairingQrBlock()` 给出终端字符画（`apps/remote-host/src/index.ts:1575`、`:1611`）；PC 界面要画图片时把矩阵按像素放大即可，不需要再引 QR 库。成本估计 2–3 天（PC UI 本体），依赖 ① 才有产品意义。

结论：**排在 ① 之后**，与 PC 侧设备管理界面（设备列表/撤销/重开配对窗口）一起做。

### 1.3 路线 ③：把配对链接改短码手输

为什么不推荐：

- 链接格式不是 UI 细节，而是协议的一部分：`wss://…/app`、`#instance`、`#token` 的语义在 protocol §1.1/§2 冻结，App 解析器严格校验（`apps/android/lib/remote_pairing.dart:127-199`）。
- 短码要成立，必须在宿主侧加一个新端点把「短码 → 完整链接/设备令牌」查出来：这等于新增一条免证书的信任路径，并且 6–8 位短码的搜索空间只有 10^6–10^8，必须配严苛限速与一次性窗口，安全性明显弱于 43 字符随机令牌 + CA 指纹固定。
- 即便做短码，也绕不开「CA 指纹 64 hex」的校验：要么短码映射到完整链接（等于把信任建立搬到宿主侧的一张表上），要么放弃指纹校验（不可接受，见 reachability §6）。
- 成本：协议改动 + 宿主端点 + App 输入 UI + 安全评审，3–5 天，且换来一个比现状更弱的信任模型。

结论：**不做**。

## 3. 已实现的终端二维码（本次改动）

### 3.1 行为

- 只在**真终端**里打印：`process.stderr.isTTY` 为真时，在配对日志行之后输出「提示 + 二维码字符画 + 明文链接」；stderr 被重定向（写日志文件、e2e 脚本捕获）时**什么都不写**（`apps/remote-host/src/index.ts:1645-1662`）。
- 触发点与配对窗口一致：启动、撤销设备后自动重开、`remoteHost.pair()` 手动重开（`apps/remote-host/src/index.ts:568`）。
- **不改变任何现有日志字段与行为**：原来的结构化日志行（`event`、`fields.pairUrl`、`expiresAt` 等）一个字都没动；二维码是额外写到 stderr 的纯文本行（`apps/remote-host/src/server.ts:320-323` 定义的日志格式不变）。e2e 脚本的配对链接来自命令行参数 `--pair-url`（`apps/remote-host/scripts/e2e-remote-host.ts:239-272`），不解析宿主 stderr；`smoke-remote-host.ts` 只测 `server.ts` 层，也不经过这段打印，所以两者行为不受影响（本轮已重跑冒烟 14/14）。
- 渲染失败只记一条 `pairing-qr-failed` warn，配对链接照常可用（同上）。
- 图像方案：1 个字符单元 = 1 模块宽 × 2 模块高，用 `▀`/`▄`/`█` + 白底黑字（`\u001b[30;47m`），四周 4 模块安静区，每行行尾 `\u001b[0m` 复位。49 模块（版本 8）的二维码占 57 列 × 29 行，53 模块（版本 9）占 61 列 × 31 行，80 列终端放得下。

### 3.2 编码实现（纯 Node，无新依赖）

- 范围：字节模式、纠错等级 M、版本 1–10（M 级数据容量 216 字节；真实配对链接 147–164 字节，落在版本 8–9）。
- 选版本、RS 纠错、交错、矩阵布置、8 种掩码打分与选择，全部实现在 `apps/remote-host/src/index.ts:937-1662`；对外只暴露 `pairingQrMatrix()`（矩阵）、`renderPairingQrBlock()`（字符画）与 `writePairingQr()`（TTY 判断 + 输出）三个函数（`apps/remote-host/src/index.ts:1575`、`:1611`、`:1645`）。
- 掩码打分刻意对齐 App 已在用的 `qr 3.0.2`（qr_flutter 的依赖）的 `_lostPoint` 规则，好处是同一段文本在本实现与手机 App 内渲染出的矩阵**逐模块相同**，可以用成熟实现互证。

### 3.3 校验（`apps/remote-host/scripts/qr-selfcheck.ts`）

运行：

```powershell
node --import tsx/esm apps/remote-host/scripts/qr-selfcheck.ts
# 或（本机 PATH 里有 tsx 时）：pnpm exec tsx apps/remote-host/scripts/qr-selfcheck.ts
```

结果（2026-11-16 本机）：**PASS 16/16**。四层断言：

1. **已知答案（KAT）**：14 段文本（3 种真实链接形态 + 版本 1–10 全覆盖）的矩阵摘要必须等于期望值；期望值由 `qr 3.0.2` 生成并逐模块对照。交叉验证方法：把两边的矩阵按各自掩码去掩码后逐位比较，**去掩码后数据位与掩码位完全一致**（包括版本 1/3/5/7/8/9/10 与多个掩码取值）。
2. 另用 `qrcode@1.5.4` 复核数据区：单字节段输入（我们只会产生这一种）**数据位逐位一致**；掩码选择不同（两家惩罚函数不同，掩码号会不一样）——两种掩码都合法，扫码无差别。`qrcode` 对 `HELLO` 这类可全字母数字的输入会自动分段（Byte+Alphanumeric+Byte），属于另一种合法编码，本实现固定用单一字节段，与 `qr 3.0.2` 一致。
3. **结构**：定位图形/分隔符/定时图形/固定深色模块、格式信息（BCH 校验 + 纠错等级 M + 掩码号与矩阵一致）、版本信息（版本 7 起）、矩阵尺寸。
4. **独立回读**：按规范蛇形顺序取数据位、去掩码、拆 RS 块，逐块验 Reed-Solomon 综合为零，再把字节段解码回原文；并验证超过版本 10 容量的输入会显式失败（不静默截断）。终端分支单独验证：伪装 TTY 时输出链接与二维码、非 TTY 时不写 stderr。

### 3.4 已知限制

- 只有宿主被直接启动、stderr 连着终端时才打印（`pnpm dsh --profile remote-host` 在终端里运行即可）；通过桌面 App 启动（stderr 不是终端）不显示——桌面/PC 界面属于路线 ②。
- 终端字体、缩放、透明背景会干扰识别；建议用等宽字体、不要在二维码区域覆盖其他输出、终端宽度 ≥ 80 列（版本 9 需要 61 列）。
- 二维码里带一次性配对令牌，只在这个配对窗口内有意义；窗口一旦被消费/过期就要重新扫码。
- 需要支持 ANSI 颜色与 Unicode 半块字符的终端（Windows Terminal、PowerShell 7、VS Code 集成终端、Windows 10+ 的 conhost 都可以）。

## 4. 扫码工具兼容性

判断依据：链接 scheme 是 `wss://`，**不是 http(s)**。扫码工具要么把它当文本处理（能复制 → 可用），要么尝试当网页打开（必然失败 → 不可用）。

### 4.1 预期可用（能拿到原始文本）

| 工具 | 使用方式 |
|---|---|
| 第三方扫码 App（如 Binary Eye 等开源扫码器、带「复制/分享原始内容」的通用扫码器） | 扫出后复制文本 → 粘贴到 App 配对页 |
| 系统相机 / Google Lens | 识别后通常会显示链接；能「复制文本」的机型可直接复制。**取决于厂商相机 UI，本轮未逐机型验证** |
| 任意能导出/复制二维码内容的 PC 扫码软件 | 若身边有电脑，扫描终端截图后再把文本转发给手机 |

### 4.2 预期不可用（会把 `wss://` 当网页）

- 微信「扫一扫」、支付宝「扫一扫」：会尝试打开链接或提示网页无效，且不提供「复制原文」。
- 系统相机直接点识别出的链接：交给浏览器打开，`wss://` 没有网页可打开。
- 任何只提供「打开链接」的扫码器。

### 4.3 真机验收清单（尚未执行）

1. 在 PC 终端启动宿主，手机用候选扫码工具扫终端里的二维码，确认能**复制出完整链接**（含 `#instance=` 与 `&token=`，长度 147–164）。
2. 粘贴到 App「添加连接」→ 连接成功，宿主日志出现 `pair-issued` 与 `connection-opened`。
3. 若扫码工具把链接做了截断/URL 编码改写（片段被丢），App 会报「缺少 #instance=…&token=… 片段」——这类工具记为不可用。
4. 记录实际可用的工具与系统版本，回填本表。
