## Summary

This directory contains the Flutter App, a Kotlin foreground service and an embedded ARM64 Node runtime. The current artifact is a development preview for Android 9 or newer; runtime and App/Web integration still require device acceptance.

## DSH migration baseline

Pocket Harness targets the complete DSH product workflow in the App. The current preview does not yet meet that target. The original [Web bundle](../../packages/bundle/web-app/cordis.patch.yml), [standard preset](../../packages/bundle/web-app/presets/standard.patch.yml), and their owning services define the behavior to migrate; retaining their Web assets or exposing a generic API does not establish App coverage. Mobile navigation can differ, but feature semantics, Session identity, authorization, persistence and conflict behavior must remain aligned with DSH.

The [migration inventory](tool/parity-manifest.json) records the original entries and the corresponding Android code and evidence. Run `node apps/android/tool/parity-audit.mjs` from the repository root to detect unclassified source changes and invalid references. This inventory check does not execute or certify the features. Core composition, App interaction, behavior tests and device acceptance are separate evidence levels; partial implementations stay partial.

DSH already provides a [Session working-directory tree](../../packages/client/ui-sidebar-files/README.md) and [document previews](../../packages/client/ui-sidebar-documentpreview/README.md) for text, code, Markdown, images, PDF, HTML, Excel and Office documents. The current conversation menu opens Session files through the original [workspaceFiles service](../../packages/api/workspace-files/README.md), preserving the working directory, file permissions, versions and change subscriptions. Directories navigate in one native page with breadcrumbs and restored scroll positions. This is distinct from App-private files, SAF grants and Session attachment IDs; those sources retain their separate authorization.

Session documents use the original reader bundles inside a document-only Android WebView, with native floating navigation. Packaged resources and a Session-bound read bridge work with Web access disabled. Binary reads use bounded chunks; closing or cancelling the page releases requests, subscriptions and retained bytes. Local Markdown images use the same Session file service and original media size policy. Links to another document in the same Session open a reading page; returning preserves the source position. Links to a line in the current file navigate without rereading it. Cross-Session and unsupported resource links report an error. The original Office converter converted a synthetic DOCX through authorized Session reads, the Android-profile Gateway and bounded PDF transfer on the host with the packaged WASM engine. Android runs each conversion in a child Node process to release its WASM memory on exit; this does not lower the device's conversion-time memory peak. Device rendering and memory behavior remain unverified. Interactive HTML preview now reads the accepted shared `ui-settings.enabled` preference. Without confirmation or when disabled it stays static; when enabled, the original reader runs scripts only in an opaque sandboxed iframe and reads bounded local JS/CSS through the bound Session. A preference change retains the reader. The document WebView still denies external HTTP(S) resources, and interactive HTML needs device acceptance. Host renderer and navigation tests do not establish Android WebView acceptance.

File pages handle directory back separately from route back, preventing recursive route vetoes. File readers reject repeated opening taps until the current reader returns. File browsers share the App atmosphere and pause ambient motion while scrolling.

Installed Build 118 retains the reviewed [android_ptc entry](tool/model-ptc-readonly.md), [workflow with reviewed child tools](tool/tool-native-workflow.md) and four [offline Linux tools](tool/linux-vm-runtime.md). Linux registration also requires the native capability and a verified Alpine image; guest-free packages expose none. The [Build 116 r28 shipped-profile check](tool/production-profile-device.md#build-116-r28) passed with `expectWorkflow=true`, following the scoped PTC, Linux and workflow lifecycle checks. The first startup timeout and earlier workflow hang remain unexplained. Original unrestricted Node PTC/workflow plugins and guest network approval remain disabled. Full upstream semantics, remaining terminal VT/OSC behavior and Office authoring remain incomplete. Root, device ADB control and offline model inference remain outside the agreed release scope.

The [real-account task records](tool/agent-service-task-device.md) cover r33 echo, r34 one Linux call across radio loss/restoration, and r35 echo plus a completion notice. They do not certify sign-in UI, avatar rendering, token refresh, reopening older conversations or notification tapping. The [115→116 upgrade](tool/upgrade-116-acceptance.md) and subsequent upgrades through 118 preserved the recorded Session bytes and SAF grants. The 117→118 r40 check retained 55 Session files totaling 1,573,622 bytes, all three SAF grants and its synthetic credential; `.cache/android/upgrade-117-118-r40-20261028.log` records that result. Build 118 also passed the [controlled native text-read checks](tool/file-tool-parity.md#build-118-device-evidence). These artifact-specific results do not certify every App interaction.

Build 117 adds [scheduled wake-up](tool/schedule-wakeup.md), disabled by default and enabled only through an explicit setting with Android exact-alarm permission. It includes restoration of the saved wake-up index after boot once credential-encrypted storage becomes available; it does not unconditionally start the Agent at boot. Natural alarm delivery, permission changes and reboot restoration still need device acceptance.

Build 118 r40 passed one real-account `android_ptc` call with one audited `list_agents` callback, a durable final reply and confirmed cleanup. With the identical production App, r41 passed one real-account workflow with one child Agent, matching parent/child durable results and confirmed cleanup. The r40 workflow failure remains recorded: its fixture used the ordinary-Session archive API for a child. r41 corrected only that test cleanup API, separately cleaned the old dedicated child without a new submission, and ran the new complete acceptance; the [ledger review](tool/parity-review.md) records these distinct results.

The Android model file tools `read`, `read_image`, `glob`, `grep`, `edit`, `present` and any dynamically loaded `str_replace_editor` are guarded at tool dispatch. Their Session directory and requested target must resolve inside the App-owned workspace. `read`, `read_image`, `write`, `edit` and `present` accept relative workspace paths; `glob` and `grep` also accept a relative or omitted search path. The guard pins the Session directory for the tool body and rechecks provider resolution so a later Session directory change cannot redirect those operations. The original `str_replace_editor` still requires an absolute file path; its directory view remains unavailable because the original two-level traversal follows child symlinks. A missing new target is allowed only when its existing ancestors prove that it remains in the workspace; ambiguous paths fail closed. This protects App-private account and runtime files outside that workspace while trusted App services retain their separate file access. A SAF document grant is used through `android_files`, never accepted as an ordinary path. `workspace-write` alone constrains mutations, not observations; this guard is a model-tool boundary, not an OS sandbox for an approved Shell or other App-UID code. Host fixtures cover private-home, symlink and similar-prefix denials; device behavior is pending acceptance.

## Build the preview

Use PowerShell 7 on Windows with Node 24, the repository's pnpm version, JDK 17, Android SDK 36, NDK 28.2.13676358, CMake 3.22.1 and Rust 1.99.1 with its `aarch64-linux-android` target. Flutter and native dependency versions are pinned in [tool/runtime-lock.json](tool/runtime-lock.json). Place the pinned Flutter checkout in the repository's ignored `.cache/flutter` directory and configure the Android SDK before continuing. Build the pinned Android ripgrep binary from a Visual Studio Developer PowerShell as described in [tool/ripgrep-android.md](tool/ripgrep-android.md).

Run the following from the repository root after `pnpm install`. The deploy command creates a new staging directory; retain that directory for subsequent App-only builds. Recreate it from a fresh deployment when the dependency lock changes. The following install restores workspace development dependencies after pnpm deploy.

```powershell
pnpm.cmd run build:artifacts
pnpm.cmd --filter dsh-python-runtime-closure deploy --legacy --prod --config.allow-unused-patches=true --config.node-linker=hoisted --config.auto-install-peers=false --config.link-workspace-packages=true --config.hoist-workspace-packages=false .cache/android/runtime-bundle
pnpm.cmd install --offline --frozen-lockfile --prod=false --ignore-scripts
./apps/android/tool/build-ripgrep.ps1 -NdkDirectory "$env:ANDROID_HOME/ndk/28.2.13676358"
node node_modules/tsx/dist/cli.mjs apps/android/tool/stage-runtime.ts
./apps/android/tool/prepare-native.ps1
node apps/android/tool/smoke-runtime.mjs
./apps/android/tool/pack-runtime.ps1
```

The native preparation script uses `http://127.0.0.1:7897` by default; supply `-Proxy` to select a different proxy. It verifies the Node archive checksum and the source revision used for the Android require-builtin addon. The staging smoke runs on the host and does not establish Android compatibility.

Run these commands from `apps/android`. The APK is written to `build/app/outputs/flutter-apk/app-debug.apk`; it uses the development signing key. Configure Gradle's HTTP/HTTPS proxy if the local network requires one.

```powershell
../../.cache/flutter/bin/flutter.bat pub get
../../.cache/flutter/bin/flutter.bat analyze --no-pub
../../.cache/flutter/bin/flutter.bat test --no-pub
../../.cache/flutter/bin/flutter.bat build apk --debug --target-platform android-arm64 --no-pub
```

Before delivery, run `tool/verify-apk.ps1` from this directory with `-ApkPath build/app/outputs/flutter-apk/app-debug.apk`, `-ExpectedVersionName` and `-ExpectedVersionCode` matching the intended build, plus `-ExpectedRuntimeSha256` from the independently packed runtime. The verifier reads the compiled Manifest and ZIP entries, requires eleven native ARM64 entries including the pinned ripgrep executable, checks its upstream license assets, and compares the embedded runtime with both its packaged and trusted SHA256. Also run `node tool/verify-document-preview.mjs build/app/outputs/flutter-apk/app-debug.apk` to check the packaged reader assets against their inventory and original module hashes. Both verifiers report JSON and exit nonzero on a mismatch. The Gradle `disable-abi-filtering` property preserves the application's explicit ARM64 filter; the APK filename does not establish its actual architectures.

## Runtime and storage

A failed or closing service instance rejects buffered runtime events and newly dispatched native work; a replacement service has an independent lifetime. Cancelling attachment selection closes a document provider's stream off the Activity thread. Cancellation does not establish that a blocked provider has stopped; the copy worker owns unpublished-file cleanup.

Replacing a ready service invalidates attachment upload receipts while retaining the selected files for explicit retry. File pages withdraw old directory actions and pagination cursors; readers can confirm the current byte position without discarding the displayed text. File-search pages preserve the query and mark old results unverified. Losing the connection does not establish that a search stopped, and reconnecting does not repeat it.

SAF text pages carry a document revision. Native reads compare document identity and metadata before and after copying, and continuation requests must present the revision from the visible page. A changed document rejects the next page instead of joining text from two revisions; the reader offers an explicit restart. Providers that silently rewrite equal-length content without changing reported metadata remain outside this check.

When the App reconnects, a failed independent status read does not suppress later conversation, settings and task reads. The first failure remains reported after the other reads complete; a replacement connection cancels the old recovery sequence. These host-tested reads do not establish device recovery after Android kills the Agent process.

If the foreground Service is unexpectedly destroyed after Node starts, it records a runtime-lost outcome before terminating the dedicated Agent process. A planned package-service replacement checks the original Agent registry, inboxes, background-job registry and plugin operations at reservation and again at commit; active or unconfirmed work refuses the switch. Safely settled work can proceed. The replacement clears its running marker but retains the process lease until exit, so the next generation cannot start while the old Node remains alive. The startup lock also prevents a concurrent Node launch from surviving unexpected shutdown. A subsequent cold start reads durable session state; it does not replay an interrupted model stream or an approval-pending tool call. A new task starting after the final Node acknowledgment remains a narrow race pending device-level shutdown acceptance; Android process-kill behavior also still needs device acceptance.

The [APK upgrade, offline and process-restart acceptance](tool/upgrade-offline-acceptance.md) checks two generations of real APK-packaged Android runtimes on the host for offline cold boot, network recovery, completed Sessions and no automatic replay. System package upgrades, Keystore, SAF grants and Android process death still require separate device acceptance.

The foreground service owns one Node instance in a private Android process. Flutter uses Binder and JSON-RPC over a dedicated local socket pair; it does not use a localhost HTTP server. Standard output and error go to the private runtime log, independently of the protocol socket. Large Binder responses use read-only shared memory. The packaged runtime launches through the named `android` dsh profile and stores its workspace and sessions in app-private storage. API credentials use Android Keystore-backed encryption; authorized document trees use persisted Storage Access Framework grants.

The Runtime Status page can request a one-shot native isolation check. An Android `isolatedProcess` service receives only a bounded, read-only file descriptor and reports its UID, input digest and denied access to a separate App-private marker. Results are cleared after a service connection change. This diagnostic validates the isolation foundation only. The original Node PTC/workflow executors remain disabled; the separately reviewed Android PTC tool has its own scoped device evidence and source-owned registration.

The same diagnostic also starts a separate isolated guest with a fixed, bounded `diagnostic.echo` frame. Its App broker admits one echo callback and checks the caller UID, request identifiers and final response. Cancellation, timeout and guest death resolve to one terminal outcome. This is a transport probe, not a script runtime or a general workflow binding; see [guest diagnostic protocol](tool/guest-echo-diagnostic.md).

The isolated worker also accepts an App-granted read-only regular-file descriptor for one request-scoped UTF-8 text read, limited to 64 KiB. The host verifies the returned text during the diagnostic. An App-side writeback foundation can commit that bounded text to an App-selected direct child of its private workspace after a revision check, cancellation checks, atomic replacement and directory sync. App-side bridge requests serialize their commits, but other same-UID writers can still race between revision checking and replacement. It is not connected to PTC or Agent execution. `node apps/android/tool/acceptance-isolated-worker.mjs` checks strict decoding, writeback bounds and cancellation on the host; Binder cancellation and UID separation still need device acceptance. This bridge does not accept paths from model output or execute JavaScript.

Android attachment, Session and ZIP publication uses a fully copied and synced temporary file followed by native `renameat2(RENAME_NOREPLACE)`. This avoids hard links denied by some devices without replacing an existing target or exposing a partial file. Original DSH hashing, collision checks, leases and append behavior remain in their owning services; other platforms retain their existing publication implementation.

Web preferences are separate from browser-editable runtime settings. The App controls the listener, scope and port; network callbacks select an explicit Wi-Fi/Ethernet IPv4 address, and an unavailable LAN address produces a waiting state. Lost service connections withdraw access links until a new observation confirms them. Late replies cannot restore an old address or erase an unsaved port. Credential rotation keeps the Agent context intact. These lifecycle paths remain subject to joint App/Web device tests.

**Network proxy** settings use the phone network/VPN or an explicit local HTTP/mixed proxy port. The glass selector shows installed FlClash, Clash Meta and v2rayNG launchers with local app icons, or opens system VPN settings; it does not control another app's VPN switch. Saved settings apply to new avatar requests. Applying them to the Agent uses the existing guarded service restart, which refuses active work, and the page reads the running process's route to confirm activation. The original HTTP proxy setup covers model and web-tool requests, with loopback bypass and no direct fallback after proxy failure. The connection test checks an HTTPS response from `www.gstatic.com`; external browsers keep their own network routing. Wi-Fi HTTP proxy/PAC and SOCKS-only ports are not configured by this page.

**Web search** combines mode selection, service parameters and credential references in one native workflow. Choosing a mode updates both search and fetch routes; unrecognized combinations remain unchanged until explicitly replaced. Saving checks each original section revision, then writes parameters and credentials before routes. Sections can partially succeed and take effect immediately; the page preserves unresolved drafts and does not automatically replay unconfirmed writes.

The Android Shell tool requests approval for each command through the original DSH tool pipeline. Only `allowed-once` permits execution; rejection, cancellation and the `never` approval policy do not. Commands run with the application's existing UID and Android permissions, without a read-only or workspace-only OS sandbox. This per-command policy belongs to the Android tool and does not describe the desktop default. Root, ADB control and offline model inference are not implemented; opt-in scheduled wake-up has its separate permission and delivery limits.

The Session resource page opens Android PTYs owned by the embedded Host. A separate ARM64 helper accepts acknowledged input and resize commands; the Host retains a bounded xterm screen across page re-entry and closes processes on explicit request or Host disposal. The mobile page projects styled cells, bounds the visible rows and style runs, and offers plain-text copy. Live input sends committed IME text in order and retains unconfirmed text after a failed write; draft input remains available for explicit submission. Control and hardware keys use PTY bytes, with arrows respecting application-cursor mode. The Host answers supported xterm and previously set OSC color queries through a bounded reply queue. Program palette and cursor settings survive page re-entry. [Terminal behavior and remaining gaps](../../docs/android-terminal.md) documents these limits. The original Web terminal controller is disabled because its `node-pty` binary is not packaged for Android. Older mouse encodings, remaining VT/OSC behavior, desktop dock behavior and real-device PTY/IME acceptance remain outstanding; the supported SGR mouse path has host coverage.

Shell timeout reporting distinguishes a termination request from a delayed deadline processed after the command has ended. The deadline remains active until output pipes close, because a successfully exited shell can leave live descendants holding them open. If process observation cannot establish the result, the tool returns `timedOut: null` with `timeoutStatus: "unconfirmed"` and a diagnostic; the App explicitly displays the uncertainty. Exit code zero alone does not clear a timeout. The default timeout remains unchanged.

**Approvals and questions** and Android notifications present the same pending DSH requests as Web. Approval buttons send the existing `allowed-once` and `rejected` outcomes. Approval notifications provide notices alongside details from the actual working directory and full original Shell command, or other tools' original arguments; details exceeding 3,500 UTF-16 code units are explicitly truncated with a prompt to open the App for the complete parameters. Simple questions can use notification options or direct text replies; complex questions open the matching App page. A plan-review question has dedicated approval and request-changes actions; request changes uses the original question dismissal instead of submitting a fabricated answer. A tool-call-keyed question remains pending for later return, while an unnamed question is cancelled as `ASK_CANCELLED`. The original question controller owns waiting, continuation and cancellation. Notification transport tokens do not grant additional permissions. Old or already answered notifications cannot reply again. The private write-ahead marker also blocks a possibly submitted reply across Host restarts. A settled original approval decision or question result now clears the old request after cold reconciliation. A still-pending `started` record remains blocked because its delivery cannot be proven. The App offers an explicit stop-current-task path with a warning that prior tool effects may already have happened; stopping does not guarantee that the original continued question is cleared. The App exposes system notification permission and channel settings.

**Background tasks** shows the original Agent queues, pending interaction links and recorded turn/job outcomes. Cancellation stops the current turn while preserving queued input; removing a queued item requires a separate confirmation. A successful cancellation request remains shown as stopping until the core reports idle. Missing or unverified history stays explicit. The subprocess page follows the original job catalog and byte-cursor output stream, with bounded output retention and explicit stop requests. After disconnection, it reconciles an unconfirmed stop against the reopened stream; late receipts cannot overwrite that state, and only the user can issue another stop request. Leaving either page does not cancel work.

**Subagents** lists a conversation's direct children and opens their nested catalogs and paged history in native pages. Browsing does not start or resume an Agent. Reads and controls for a session-backed child use its direct-parent and child addresses, validated by the original services. One-shot children and children whose type remains unknown have read-only history; external entries do not get fabricated session history. A continuable child can receive text through the original `queue` or `steer` operation when its parent is available. The original parent interruption operation stops the current turn and retains queued input. An unconfirmed submission keeps its draft and request identity within the current App process; refresh and reconnect only read state and never resend it automatically. This pending draft does not survive App process death. A send receipt confirms acceptance, not completed work.

**Background execution** shows the foreground service's actual task summary, CPU wake-lock state and system battery restrictions, with an entry to Android's application settings. A connection change immediately withdraws old task and wake-lock observations; late reads and setting receipts cannot confirm a replacement service. An unconfirmed setting remains visible within the current page for comparison after a fresh read and is never resent automatically. Optional CPU protection uses a bounded, renewable wake lock only while fresh core state reports active Agent work or background jobs. Waiting requests and queued input alone do not hold it; stale state releases protection and displays an unconfirmed status. Network-change callbacks are coalesced and fenced at service teardown. If the runtime transport fails, the dedicated Agent process stops so Node cannot continue work without status or cancellation; a later launch reads interrupted records without replaying work. A synchronous App-private receipt stores only the interruption type and time before that stop; the task page shows it after a cold start and asks the user to inspect the original conversation rather than implying that its result is known. A corrupt or unavailable receipt is reported as unconfirmed. The process also stops on a foreground-service timeout. Android Shell starts under a native parent-death supervisor that kills its process group if Agent dies. Android emulator fault injection covers this path, including a background descendant with closed output; ARM64 phone behavior and commands that deliberately create a new session remain unverified. These mechanisms do not guarantee survival if Android stops the process.

The optional **transparent overlay keepalive** is off by default. Enabling it requires Android's display-over-other-apps permission. The service attaches a one-physical-pixel, fully transparent, non-touchable overlay only while its current task state reports active work; completion, stale state, permission revocation and service shutdown remove it. Settings show the requested switch separately from the observed attachment state. Android may still end the process, and a fully transparent pixel does not qualify as the visible overlay required for Android 15's background foreground-service start exemption. No task or tool is replayed automatically to compensate for a process death.

A timed-out or failed task-summary poll does not revoke a newer pushed task observation while its bounded lease remains valid; expiry still releases the CPU wake lock and task notification. Repeated `ready` signals preserve that expiry timer. A conflicting summary with the same epoch and revision is rejected instead of silently changing the active counts. These state transitions have host tests but need device acceptance.

A successfully completed Agent task can post one short Android notification linking to its conversation. It previews up to 100 characters from the last recorded assistant text of that turn; a turn without text uses the fixed completion message, never tool output. The notification is marked private; lock-screen display follows system settings, and a visible conversation suppresses the notice. A queued notice is discarded if a newer completion for the same conversation supersedes it before delivery. The Service gives accepted completion-watermark writes at most 250 ms to finish during teardown and posts only notices whose watermark was committed. A sudden process death or write failure can still omit a notice; cold start reads the recorded Session result and never replays a historical completion as a fresh alert or task. Errors, cancellation, interrupted history and reconnect do not produce a success notice. Android notification permission and system notification settings still apply.

**Automations** uses the original schedule catalog, task edits, deletion and delivery history. The App filters tasks, edits active tasks' names, prompts and timing rules, and links back to their conversations. Creation opens a conversation for the Agent's existing scheduling tools; the App does not add pause or run-now operations. Edits compare the original task record and retain the draft on conflict or an unconfirmed result. Delivery history records reminders reaching a conversation, not completed model work.

The Android-profile Host smoke also creates a short one-shot reminder through the model tool, waits for its durable delivery receipt, and checks that exactly one scheduled input reached the owning Session before the task retired. A successful smoke run removes its synthetic home. This host check does not establish lock-screen or device-restart behavior.

**The chat plus menu** follows DSH's Add and Commands groups and the runtime's actual command catalog. Android currently disables desktop sandbox permission presets; no substitute permission menu is fabricated. Session creation, files and non-model commands work before credentials are configured. Files use the system document picker and original session-scoped upload receipts; failed uploads retain the selected files for retry. PNG, JPEG, WebP and GIF use the original image validation, normalization and message admission through Sharp's official WASM runtime. Image sends remain subject to the selected model's input capabilities. Commands execute through the original command service. ZIP export uses the original session-log format and a system save picker.

Typing a leading `/` now searches the effective Session command catalog and skills in one inline panel. Command names and first-party localized titles use prefix-first subsequence matching; a selected command consumes the typed trigger and uses the same action as the plus menu, while a selected skill remains ordinary prompt text. A directory failure stays visible and leaves the skill rows usable. Typed lines still resolve through the original command identity and attachment rules on submission; unmatched slash text remains an ordinary message. The mobile panel does not yet implement the desktop Web menu's Arrow/Tab keyboard selection, command contribution decorations, or persistent host input chips. Its behavior has widget-test evidence but no phone acceptance.

Selected images and images referenced by the conversation open in a native zoomable viewer with retry and close controls. Historical reads use the original Session authorization; the viewer never opens an arbitrary device path. Previews have a separate 20 MiB encoded-byte limit and a bounded decode size. A failed preview does not delete the draft or change the original upload limits.

Historical file attachments open a native reader from the conversation. The original Session query authorizes the exact file reference, and the attachment store verifies its complete contents before exposing a temporary copy. UTF-8 text uses bounded pages; other formats offer the system Save As picker. Saving checks the original length and SHA256. Connection changes retain displayed text as unverified and never repeat a save; cancellation waits for copying to stop, and failures identify potentially incomplete destination files. Reading and saving neither activate an Agent nor alter the conversation.

**Conversation rendering** uses the original message source to distinguish user input from injected context. Context and system prompts stay out of the reading flow and remain inspectable in Session Records. Replies render GitHub-flavored Markdown, including tables, lists and code blocks. Status and failure events occupy compact rows; a failure keeps the first line of its reason visible and opens the full text and diagnostics on demand. A lazy list builds visible conversation rows and retains disclosure state; streaming replies use their original attempt identity so retries remain distinct. The first text arriving in an empty live reply now fades in at paint time without shifting layout; reduced motion displays it immediately. This entrance has widget-test coverage but has not been verified on a phone.

Planning, reasoning and tool activity share one transparent execution chain per recorded Turn. Active chains start expanded; successful turns automatically fold to one completion row and can then be reopened. Failed, stopped and unconfirmed outcomes retain distinct labels. Expanded steps show compact queries, two source previews, consecutive webpage reads and recorded plans. Full tool output opens in the existing live detail viewer; authored answers and their copy actions remain separate. Each step remains a lazy list row. Site marks reuse the Web host mapping and bundled Simple Icons artwork; unknown hosts use a globe, without favicon network requests. Regenerate marks with `node apps/android/tool/generate-site-marks.mjs`, then format the generated Dart file.

Each completed reply's More menu can create a new conversation branch at that reply's recorded `turn/end` sequence through the original `library.sessionFork` service. The child title follows the original numbered-fork convention when the source has a saved title. A confirmed branch opens after its history loads; if opening or the child-title update fails, the App reports the created session ID for retrieval from Workspaces and Sessions. Unconfirmed or partially completed forks are never automatically retried. This reply action has host-test coverage but has not been exercised on a phone.

On cold reading after an Agent process death, the App uses the original interrupted-history projection. It presents the recorded partial reply and unknown tool outcome as interrupted, without modifying the raw session log or claiming a completed tool result. Queued input is retained by the original core; the killed model turn is not resumed or replayed automatically.

Session-list reads are scoped to the runtime connection generation. A replacement connection can load its own list while an old request is still pending; a late old result or error cannot replace the new list. Opening a long conversation merges live events received during history paging by sequence number, avoiding repeated whole-history scans.

Reasoning details retain the compact preview text size. Disclosure uses blur and fade in both directions; streaming updates do not restart it. Automatic completion folding keeps the visible answer at the same screen position during layout without changing its text height. At the top, only the space that cannot be offset by scrolling is retained and consumed by a subsequent drag; user scrolling takes precedence. Markdown requires double tildes for strikethrough, leaving single-tilde numeric ranges intact. Sending a message smoothly lifts that question above the Agent activity; space below it shrinks as the reply grows, and a user drag cancels positioning.

**Model file tools** use the original `read`, `write` and `edit` implementations with the [filesystem sandbox provider](../../packages/fs/fs-sandbox/README.md). The Android profile defaults mutations to the workspace and permitted temporary roots; a wider retry requires the original approval for that one invocation. Overwriting or editing an existing file retains the original observed-version checks, and an edit requires a unique literal match unless `replace_all` is selected. The original `fs-sandbox` entry is disabled because `android-filesystem` subclasses that provider. Its [Android adapter](runtime/android-filesystem.mjs) publishes new files through the existing copy-and-exclusive-rename bridge instead of hard links, preserving the original version checks and approval policy. The [staged-profile smoke](tool/smoke-file-tools.mjs) exercises real host filesystem operations, rejection, cancellation and cold recovery through a synthetic local model. Android Binder and device filesystem acceptance remain unverified. This policy does not confine `android_shell` at the kernel level or restore the original `/permission` menu.

SAF image model reads now admit at most two provider streams at once. Each request carries a cancellable ID; cancellation received before admission prevents that read from starting, while authorization revocation or Service shutdown cancels active reads. A full reader returns an explicit retryable error before opening another provider stream. The [host request-lifecycle check](tool/acceptance-document-image-requests.mjs) covers these transitions; actual provider cancellation and memory behavior still require device acceptance.

**Execution permissions** in Settings read a fresh runtime-owned policy snapshot. The screen distinguishes the original file-tool sandbox mode from the normal Android Shell policy, which does not register a model tool until an isolated executor exists. An explicit internal migration mode retains App-UID Shell with one-invocation approval and is labeled unconfined. The page discards observations after a runtime connection change and exposes pending approval requests without a fictitious preset switch.
